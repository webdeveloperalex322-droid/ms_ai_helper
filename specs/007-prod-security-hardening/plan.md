# Implementation Plan: Production Security Hardening (P0)

**Branch**: `007-prod-security-hardening` | **Date**: 2026-07-18 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/007-prod-security-hardening/spec.md`

## Summary

Закрыть блокеры безопасности, не позволяющие выкатить сервис в продакшен: ввести двухконтурную проверку ключей доступа через единый Guard, ограничить частоту запросов, сузить CORS, запретить старт с заглушечными секретами, починить панель администратора в образе и защитить её куку, прекратить утечку внутренних сообщений об ошибках, привести публикуемую документацию API в безопасный вид.

Технический подход: один глобальный `APP_GUARD`, управляемый метаданными на уровне маршрута (по умолчанию закрыто, открытие — явным декоратором); `@nestjs/throttler` с двумя именованными профилями и подменённым `getTracker`; расширение существующей zod-схемы конфигурации проверками, срабатывающими только при `NODE_ENV=production`; санитизация ветки не-`HttpException` в существующем фильтре; сборка Swagger-документа в двух вариантах по режиму.

Ключевое архитектурное ограничение, найденное при разведке: **панель AdminJS монтируется на «сырой» инстанс Fastify** (`src/modules/admin/admin.module.ts:107-114`) и полностью минует конвейер Nest. Глобальный Guard её не покроет — её защита остаётся на собственном механизме AdminJS, и работать с ней нужно отдельно.

## Technical Context

**Language/Version**: TypeScript 5.7, Node >= 22

**Primary Dependencies**: NestJS 10.4 + Fastify 5 (`@nestjs/platform-fastify`), zod 3 (валидация конфигурации), `@nestjs/swagger` 8, AdminJS 7 (`@adminjs/fastify`, `@adminjs/sql`), Drizzle ORM 0.38 + pg 8.
Добавляется одна зависимость: **`@nestjs/throttler` ^6.5.0** — peer-диапазон `@nestjs/core` включает `^10.0.0`, конфликта с текущей версией нет (проверено).

**Storage**: PostgreSQL 15/16 + pgvector. **Схема БД данной задачей не затрагивается — миграции не создаются.** Ключи доступа живут в конфигурации развёртывания (решение зафиксировано в спецификации), счётчики частоты — в памяти процесса.

**Testing**: Vitest 2.1. Юнит-тесты рядом с кодом (`src/**/tests/*.spec.ts`), e2e — `test/e2e/**` с отдельным `vitest.e2e.config.ts`.

**Target Platform**: Linux-контейнер за nginx с завершением TLS (`docker/nginx/conf.d/mshelper.conf`), один экземпляр приложения.

**Project Type**: Модульный монолит — веб-сервис на NestJS.

**Performance Goals**: Проверка ключа и учёт частоты выполняются до обращений к БД и внешним провайдерам; накладные расходы на запрос — единицы миллисекунд. Числовые пороги частоты спецификацией сознательно не фиксируются (FR-013).

**Constraints**:

- Существующее функциональное поведение для запросов с действительным ключом не меняется (SC-009): 122 текущих теста должны проходить без правок логики.
- Счётчики частоты — в памяти; горизонтальное масштабирование вне объёма.
- Guard не покрывает `/admin` и `/public/` — они вне конвейера Nest.

**Scale/Scope**: Единицы сторонних интеграторов, один экземпляр приложения. Затрагивается 13 HTTP-маршрутов в 6 контроллерах плюс панель AdminJS и раздача статики.

## Подход по историям спецификации

### История 1 и 2 — разграничение доступа (FR-001 — FR-010e)

**Модель «закрыто по умолчанию».** Глобальный `APP_GUARD` применяется ко всем маршрутам Nest. Открытие и смена контура — исключительно декораторами:

- без декоратора → требуется клиентский ключ (публичный контур);
- `@InternalRoute()` → требуется служебный ключ, клиентский отклоняется (FR-003);
- `@PublicRoute()` → ключ не требуется (только `GET /v1/health`, FR-008).

Инверсия по сравнению с сегодняшним состоянием умышленна: забытый декоратор делает новый маршрут закрытым, а не открытым. Сейчас ровно наоборот — забытый вызов `checkAuth` делает маршрут публичным (`suggestion-admin.controller.ts:36,44,55`).

**Guard регистрируется как `APP_GUARD`-провайдер в `AppModule`, а не через `app.useGlobalGuards(new …)` в `main.ts`.** Причина: Guard нуждается в `ConfigService`, а объекты, созданные через `new` в `main.ts` (как текущие фильтр и интерцептор, `main.ts:41-42`), внедрение зависимостей не получают.

**Постоянное по времени сравнение** (FR-005): `crypto.timingSafeEqual` над буферами. Требует равной длины — предъявленный ключ сначала приводится к хешу фиксированной длины (SHA-256), сравниваются хеши. Это устраняет и утечку длины ключа, и исключение при несовпадении размеров буферов.

**Фазовый режим** (FR-010a — FR-010e): Guard читает режим из конфигурации. В режиме наблюдения при неудачной проверке клиентского ключа — запись в лог и `return true`. Служебный контур режим наблюдения игнорирует всегда (FR-010d).

**Атрибуция потребителя**: при успешной проверке Guard кладёт `{ label }` на объект запроса. Оттуда её берут интерцептор логирования (FR-009b) и трекер частоты (FR-009c).

### История 1 — ограничение частоты (FR-011 — FR-015)

`ThrottlerModule` с двумя именованными профилями: `costly` (эндпоинт с платными вызовами) и `standard` (остальной публичный контур). Пороги — из конфигурации (FR-013).

`ConsumerThrottlerGuard extends ThrottlerGuard` с переопределённым `getTracker`: метка владельца, если Guard доступа её проставил, иначе `req.ips?.[0] ?? req.ip` (FR-011).

**`trustProxy: true` в `FastifyAdapter` обязателен** (FR-015): без него `req.ips` пуст и все запросы за nginx считаются одним источником — ограничение перестаёт различать клиентов. Это ровно тот случай, когда мера выглядит работающей, но не работает.

Порядок Guard'ов в `AppModule` значим: сначала проверка ключа (чтобы метка была проставлена), затем ограничение частоты. Nest выполняет `APP_GUARD`-провайдеры в порядке объявления.

`@SkipThrottle()` — на `/v1/health` и на служебный контур (операторы, не анонимы).

### История 3 — конфигурация (FR-016 — FR-022)

Существующая функция `validateConfig` (`configuration.ts:45`) уже имеет ветку послепроверок для `OPENAI_API_KEY` — новые проверки продакшена добавляются туда же, единым блоком, срабатывающим только при `NODE_ENV === 'production'`.

Проверяется: заданность, несовпадение с перечнем известных заглушек, минимальная длина (32 / 12 по FR-018), уникальность ключей и меток (FR-009e). Сообщение называет переменную и не печатает значение (FR-019).

Дефолты для `INTERNAL_API_KEY`, `ADMIN_USER`, `ADMIN_PASSWORD`, `ADMIN_COOKIE_SECRET` **сохраняются** — их удаление сломало бы разработку и 122 существующих теста (FR-020). Безопасность обеспечивается именно продакшен-проверкой, отвергающей эти же значения как заглушки.

### История 4 — панель администратора (FR-023 — FR-026)

**Она вне конвейера Nest.** `onModuleInit` получает «сырой» Fastify через `HttpAdapterHost` и вызывает `buildAuthenticatedRouter` (`admin.module.ts:107-114`). Ни глобальный Guard, ни ограничение частоты, ни фильтр исключений, ни интерцептор логирования на `/admin` не действуют. Это принимается как есть: собственная аутентификация AdminJS остаётся её механизмом защиты, задача — сделать его корректным.

Правки: `cookie.secure` по режиму вместо жёсткого `false` (`admin.module.ts:128`); `httpOnly`; постоянное по времени сравнение в `authenticate` (`:117-122`) вместо `===`; единое сообщение об отказе (FR-026); внесение `ADMIN_*` в `.env.prod`, где их сейчас нет.

**Починка образа (FR-023)** — предмет исследования, а не готовое решение: пути компонентов резолвятся в `src/` (`:63,67,71`), которого в образе нет (`Dockerfile:13`). Проверяемая гипотеза и запасной вариант — в [research.md](./research.md); эта задача требует фактической сборки образа, а не рассуждения.

### История 5 — ошибки (FR-027 — FR-029)

Правится единственная ветка `else if (exception instanceof Error)` (`http-exception.filter.ts:42-45`): логирование остаётся полным, в тело ответа вместо `exception.message` идёт обобщённое сообщение плюс `requestId`, снятый с запроса (его уже проставляет интерцептор, `logging.interceptor.ts:16`). Ветка `HttpException` не трогается — ошибки валидации продолжают доходить до клиента (FR-029).

Фильтр перерегистрируется как `APP_FILTER`, чтобы получить `ConfigService` и возвращать подробности в режиме разработки (FR-029, сценарий 4).

### История 6 — источники и документация (FR-030 — FR-036)

CORS: `app.enableCors({ origin: <список из конфигурации>, credentials: false })`. В продакшене пустой список — ошибка конфигурации, а не «разрешить всё» (FR-031).

**Проверить фактическим тестом**: обрабатывает ли `@fastify/cors` предварительный запрос до Guard'ов. Если предварительный запрос дойдёт до Guard, публичный контур перестанет работать из браузера — это разрушительный отказ, и он должен быть покрыт e2e-тестом, а не предположением.

Swagger: два варианта документа. В продакшене — `SwaggerModule.createDocument(app, config, { include: [<модули клиентского контура>] })`, служебные модули исключены (FR-033). В разработке — полный документ (FR-036). В обоих — `.addApiKey()` со схемой заголовка, чтобы работала подстановка ключа (FR-034).

Заодно устраняется двойной префикс `/v1/v1/import/*` (`import.controller.ts:74`): живых вызывающих нет (проверено обходом `scripts/`, `test/`, `test-client/`, `public/`, `seeds/`), а документация репозитория уже описывает `/v1/import/*` — правка приводит код в соответствие с ней.

## Порядок работ и связи

```text
Конфигурация (перечень ключей, проверки)      ← фундамент, первым
        │
        ├──► Guard доступа + декораторы ──► применение к контроллерам ──► e2e по маршрутам
        │              │
        │              └──► Ограничение частоты (нужна метка владельца)
        │
        ├──► Swagger по режиму (нужна схема ключа)
        └──► Панель: cookie, сравнение, .env.prod

Независимые ветки, выполняются параллельно:
        • Фильтр исключений (санитизация)
        • Починка образа (требует сборки)
        • CORS + trustProxy + bodyLimit
```

Проверка ключей вводится в режиме наблюдения и переводится в принудительный отдельным шагом — это последнее действие выкатки, а не часть разработки.

## Риски

| Риск | Последствие | Как снимается |
|---|---|---|
| Предварительный запрос браузера доходит до Guard | Публичный контур не работает из браузера — полный отказ | Отдельный e2e-тест на предварительный запрос до перевода в принудительный режим |
| `trustProxy` не включён | Ограничение частоты видит один источник и бесполезно | Тест, проверяющий разделение счётчиков по заголовку исходного адреса |
| Панель не собирается в образе | Приложение падает при старте в продакшене | Обязательная фактическая сборка образа, а не только прохождение тестов |
| `APP_GUARD` ломает существующие тесты | 122 теста, поднимающие модули | Тестовая конфигурация сохраняет дефолты; проверка продакшена не срабатывает при `NODE_ENV=test` |
| Ожидание, что Guard защитит `/admin` | Ложное чувство покрытия | Зафиксировано в плане и в ADR; e2e-тест проверяет `/admin` отдельно |
