# Phase 1 — Data Model: Production Security Hardening

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

> **Схема базы данных не затрагивается.** Миграции этой задачей не создаются. Все сущности ниже — конфигурационные либо живущие в памяти процесса на время запроса.

---

## 1. AccessKeyEntry — запись перечня клиентских ключей

Источник: переменная окружения `CLIENT_API_KEYS`, разбирается при старте.

| Поле | Тип | Правила |
|---|---|---|
| `label` | строка | Непустая. Алфавит `[a-z0-9_-]`, 1–32 символа. Уникальна в перечне (FR-009e). Попадает в логи и в ключ счётчика частоты |
| `key` | строка | Непустая. В продакшене — не короче 32 символов и не входит в перечень известных заглушек (FR-017, FR-018). Уникальна в перечне (FR-009e). **Никогда не логируется** (FR-010) |
| `keyHash` | Buffer | Производное: SHA-256 от `key`, вычисляется один раз при старте. Используется для постоянного по времени сравнения (R4). В конфигурации не задаётся |

**Формат в окружении:** `метка:ключ` через запятую.

```
CLIENT_API_KEYS=web-widget:aaaa…,partner-acme:bbbb…
```

**Правила разбора:** пустые записи после разделения игнорируются; пробелы по краям обрезаются; запись без разделителя `:` либо с пустой частью — ошибка конфигурации с указанием позиции записи, но **без вывода её содержимого** (FR-019).

## 2. AccessScope — контур доступа маршрута

Перечисление, задаётся метаданными на обработчике или контроллере. Значение по умолчанию при отсутствии декоратора — `client`.

| Значение | Декоратор | Требуемый ключ | Применение |
|---|---|---|---|
| `client` | *(отсутствует — значение по умолчанию)* | Любой из `CLIENT_API_KEYS` | Публичный контур ассистента, подсказки, события |
| `internal` | `@InternalRoute()` | Только `INTERNAL_API_KEY` | Импорт каталога, управление подсказками |
| `public` | `@PublicRoute()` | Не требуется | Только `GET /v1/health` |

**Инвариант:** клиентский ключ никогда не удовлетворяет `internal` (FR-003). Обратное направление не рассматривается — служебный ключ на клиентском маршруте не предусмотрен и трактуется как недействительный.

**Разрешение при конфликте:** метаданные обработчика приоритетнее метаданных контроллера.

---

## 3. Consumer — потребитель, распознанный на время запроса

Проставляется Guard'ом на объект запроса при успешной проверке. Живёт только в пределах запроса, нигде не сохраняется.

| Поле | Тип | Назначение |
|---|---|---|
| `label` | строка | Метка владельца ключа либо `internal` для служебного контура. Идёт в лог (FR-009b) и в ключ счётчика частоты (FR-009c) |
| `scope` | `AccessScope` | Контур, по которому прошла проверка |

**Отсутствует**, если ключ не предъявлен и маршрут открыт (`public`), либо если запрос пропущен в режиме наблюдения. В этих случаях учёт частоты ведётся по адресу клиента (FR-011).

## 4. EnforcementMode — режим ввода проверки

Источник: `ACCESS_CONTROL_MODE`. Значение по умолчанию — `enforce` (FR-010e).

| Значение | Поведение клиентского контура | Поведение служебного контура |
|---|---|---|
| `enforce` | Неверный или отсутствующий ключ → отказ | Отказ |
| `observe` | Неверный или отсутствующий ключ → запрос обслуживается, факт пишется в лог (FR-010b) | **Отказ — режим наблюдения на служебный контур не распространяется** (FR-010d) |

**Переходы состояний:** только через изменение конфигурации и перезапуск. Переключение во время работы не предусмотрено. Ожидаемое направление при выкатке — `observe` → `enforce`, единожды; обратный переход означает откат.

## 5. ThrottleProfile — профиль ограничения частоты

Два именованных профиля, пороги задаются конфигурацией (FR-013).

| Профиль | Переменные | Применяется к | Причина обособления |
|---|---|---|---|
| `costly` | `THROTTLE_COSTLY_LIMIT`, `THROTTLE_COSTLY_TTL_SEC` | `POST /v1/assistant/product-answer` | Каждый запрос инициирует платные внешние вызовы (FR-012) |
| `standard` | `THROTTLE_STANDARD_LIMIT`, `THROTTLE_STANDARD_TTL_SEC` | Остальной клиентский контур | Обычная защита от злоупотребления |

**Единица учёта** (FR-011): `Consumer.label`, если потребитель распознан; иначе исходный адрес клиента — `req.ips[0]` при включённом `trustProxy`, иначе `req.ip`.

**Не применяется:** `GET /v1/health` и служебный контур (`@SkipThrottle()`).

## 6. Перечень критичных секретов

Проверяется единым блоком при `NODE_ENV === 'production'` (FR-016 — FR-018).

| Переменная | Минимальная длина | Дефолт-заглушка, подлежащий отвержению |
|---|---|---|
| `CLIENT_API_KEYS` | 32 на каждый ключ | *(дефолта нет — в продакшене обязательна)* |
| `INTERNAL_API_KEY` | 32 | `dev-internal-key-change-in-prod` |
| `ADMIN_USER` | — *(проверяется только на отличие от заглушки)* | `admin@example.com` |
| `ADMIN_PASSWORD` | 12 | `changeme123` |
| `ADMIN_COOKIE_SECRET` | 32 | `dev-cookie-secret-replace-in-prod-!!!` |

**Инвариант формулировки ошибки:** сообщение называет переменную и характер нарушения (не задана / совпадает с заглушкой / короче минимума), но никогда не печатает ни фактическое, ни ожидаемое значение (FR-019).

**Дефолты сохраняются в схеме** — они нужны разработке и тестам (FR-020). Защиту даёт не их удаление, а отвержение этих же значений в продакшене.

## 7. ErrorResponse — тело ответа об ошибке

Изменяется существующая форма (`src/common/filters/http-exception.filter.ts:47-53`).

| Поле | Присутствие | Содержимое |
|---|---|---|
| `error.code` | всегда | Как сейчас |
| `error.message` | всегда | Для `HttpException` — как сейчас (FR-029). Для прочих исключений — обобщённая формулировка **без текста исходного исключения** (FR-027) |
| `error.details` | только при ошибке валидации | Как сейчас |
| `error.requestId` | **новое**, всегда | Идентификатор запроса, уже проставляемый интерцептором (`logging.interceptor.ts:16`); связывает ответ с полной записью в логе (FR-028) |

**Обратная совместимость:** поля добавляются, существующие не переименовываются и не удаляются — потребители, читающие `error.code` и `error.message`, не ломаются.
