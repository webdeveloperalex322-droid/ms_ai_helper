# Contract — Access Control

**Feature**: [../spec.md](../spec.md) | **Data model**: [../data-model.md](../data-model.md)

Контракт между сервисом и его потребителями: заголовки, коды ответов, тела. Это внешне наблюдаемое поведение — по нему пишутся e2e-проверки.

---

## Заголовки

| Заголовок | Контур | Значение |
|---|---|---|
| `X-API-Key` | клиентский | Один из ключей перечня `CLIENT_API_KEYS` |
| `X-Internal-API-Key` | служебный | `INTERNAL_API_KEY` |

Существующий заголовок `x-internal-api-key` уже используется эндпоинтами управления подсказками (`suggestion-admin.controller.ts:35,43,53`) — **имя сохраняется**, меняется только механизм проверки (ручной вызов → Guard). Ломающего изменения для служебного контура нет.

Имена заголовков сравниваются без учёта регистра (нормальное поведение HTTP).

## Ответы

### Успешная проверка

Поведение обработчика не меняется — коды и тела те же, что сейчас (SC-009).

### Отказ в доступе

```
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Access denied",
    "requestId": "<uuid>"
  }
}
```

**Инвариант неразличимости** (FR-006): ответ **побайтово одинаков** для случаев «заголовок отсутствует», «ключ неверен», «предъявлен клиентский ключ на служебном маршруте». Ни код, ни формулировка, ни наличие дополнительных полей не должны различать эти случаи. Причина отказа пишется только в лог.

Различие во времени формирования ответа также недопустимо (FR-005) — отсюда хеширование и перебор перечня без раннего выхода.

### Превышение лимита частоты

```
HTTP/1.1 429 Too Many Requests
Retry-After: <секунды>

{
  "error": {
    "code": "TOO_MANY_REQUESTS",
    "message": "Rate limit exceeded",
    "requestId": "<uuid>"
  }
}
```

Заголовок `Retry-After` обязателен (FR-014). Платные внешние вызовы для отклонённого запроса не выполняются — отказ происходит до входа в обработчик.

### Внутренняя ошибка

```
HTTP/1.1 500 Internal Server Error

{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "Internal server error",
    "requestId": "<uuid>"
  }
}
```

Текст исходного исключения, фрагменты SQL, пути файловой системы и параметры подключения в теле отсутствуют (FR-027). Полная диагностика — в логе, под тем же `requestId` (FR-028).

## Предварительные запросы браузера

`OPTIONS` на любом маршруте обслуживается механизмом CORS **без предъявления ключа**. Браузер не передаёт пользовательские заголовки в предварительном запросе, поэтому требование ключа сделало бы публичный контур неработоспособным из браузера.

Ответ содержит заголовки разрешения только если `Origin` входит в `CORS_ALLOWED_ORIGINS` (FR-030).

---

## Режим наблюдения

При `ACCESS_CONTROL_MODE=observe` запрос клиентского контура без ключа или с неверным ключом **обслуживается штатно**, а в лог пишется запись о том, что в принудительном режиме он был бы отклонён (FR-010b): маршрут, исходный адрес, факт отсутствия либо неверности ключа. Значение предъявленного ключа не логируется.

Служебный контур в этом режиме продолжает отклонять (FR-010d).

## Документация

`/v1/docs` доступна в продакшене (FR-032).

- Публикуются **только** маршруты клиентского контура и `GET /v1/health`. Маршруты импорта и управления подсказками в документ не входят (FR-033).
- Объявлена схема доступа по заголовку `X-API-Key`; интерфейс документации позволяет подставить выданный ключ и выполнить пробный запрос (FR-034).
- Примеры не содержат действительных ключей и идентификаторов реальных торговых сетей (FR-035).
- В режиме разработки публикуется полный набор маршрутов, включая служебные (FR-036).

## Логирование

В строку лога запроса добавляется метка владельца ключа (FR-009b). Значение ключа не логируется ни при каких условиях (FR-010) — ни в строке запроса, ни в сообщениях об ошибках, ни в трассировках.

Существующий интерцептор пишет `req.url` целиком, вместе со строкой запроса. Ключ передаётся заголовком, а не параметром запроса, поэтому в текущей форме утечки нет — но при вводе передачи ключа параметром запроса она возникнет немедленно. Такой способ передачи не предусмотрен.
