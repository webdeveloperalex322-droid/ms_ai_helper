# Tasks: Production Security Hardening (P0)

**Input**: Design documents from `/specs/007-prod-security-hardening/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Tests**: Включены. Спецификация формулирует критерии приёмки как проверяемые утверждения (SC-001 — SC-011), а план выделяет два разрушительных отказа (предварительный запрос браузера, `trustProxy`), которые проявляются только на исполнении. Тесты здесь — не факультативное дополнение, а единственный способ отличить «выглядит рабочим» от «работает».

**Organization**: По историям спецификации. Три истории приоритета P1 закрывают денежный и разрушительный риск; они и составляют минимальный выкатываемый объём.

- **[Story]**: Принадлежность истории (US1 — US6)
- Пути указаны от корня репозитория

> **Отступление от плана при исполнении.** Тесты T018, T020, T020a задумывались в `test/e2e/**` против настоящего приложения. Приложение сейчас **не поднимается из `dist`** — `node dist/src/main` падает на сборке компонентов AdminJS (`Cannot find package '@babel/plugin-syntax-import-assertions'`), то есть ровно тем способом, которым стартует Docker-образ. Поэтому тесты реализованы как конвейерные, на сокращённом модуле с настоящими Guard'ами:
>
> - `src/common/security/tests/guard-pipeline.spec.ts` — контуры доступа и предварительный запрос браузера (T018)
> - `src/common/throttling/tests/throttling-pipeline.spec.ts` — лимиты, `Retry-After`, разделение счётчиков (T020)
> - `src/common/security/tests/key-revocation.spec.ts` — отзыв ключа (T020a)
> - `src/common/interceptors/tests/logging.interceptor.spec.ts` — атрибуция в журнале (T020b)
>
> Они проверяют цепочку Guard'ов по-настоящему, поверх HTTP, но **не** проверяют, что декораторы расставлены на всех настоящих контроллерах. Этот пробел закрывает T033 — и он останется открытым, пока не починен запуск из `dist` (T055 — T058, US4).
>
> **T029 дал результат, отличный от ожидаемого — дважды.**
>
> 1. Библиотека при именованных профилях ставит `Retry-After-costly`, а не `Retry-After`; канонический заголовок никто не выставляет. Добавлен в `ConsumerThrottlerGuard` — в guard, как и предписывала задача, не в фильтр исключений.
> 2. **Тело ответа `429` не соответствовало контракту, и это выяснилось только на живом приложении.** `ThrottlerException` отдаёт свой ответ **строкой**, а не объектом; ветка фильтра для строк задавала лишь `message`, оставляя `code` начальным значением `INTERNAL_ERROR`, и отправляла клиенту `"ThrottlerException: Too Many Requests"` — то есть имя внутреннего класса. Ни один тест это не ловил: конвейерные проверки смотрели статус и заголовок, но не тело. Исправлено в `http-exception.filter.ts`, добавлен регрессионный тест.
>
> Урок для оставшихся историй: статус ответа и его тело — разные утверждения, и проверять надо оба.

> **Корневая причина незапуска из `dist` найдена и устранена.** AdminJS указывает babel-плагин **строкой** — `plugins: ['@babel/plugin-syntax-import-assertions']` (`node_modules/adminjs/lib/backend/bundler/components.bundler.js`). Пресеты он импортирует объектами и те резолвятся из его собственного каталога, а строку babel резолвит от корня проекта, где при изоляции pnpm пакета нет. Плагин добавлен в **prod-зависимости** приложения — он нужен в рантайме, при сборке компонентов на старте. После этого `node dist/src/main` поднимается, что разблокировало T032 и живую проверку вообще.
>
> **Новая связка, обнаруженная при проверке: `TRUST_PROXY` стал обязательным для работы панели.** С `cookie.secure = true` в продакшене `@fastify/session` **не ставит куку вовсе**, пока не видит защищённое соединение. За nginx это означает, что нужны одновременно `TRUST_PROXY=true` и заголовок `X-Forwarded-Proto: https` (nginx его уже шлёт — `docker/nginx/conf.d/mshelper.conf:41`). Без этого вход внешне проходит — редирект на `/admin` возвращается, — но сессии нет, и оператор остаётся незалогиненным. Симптом не похож на проблему с флагами куки и уводит отладку в сторону.
>
> `.env.prod` сейчас **не задаёт** ни `TRUST_PROXY`, ни `ADMIN_USER` / `ADMIN_PASSWORD` / `ADMIN_COOKIE_SECRET`. Пока T049 (US3) не выполнен, продакшен-развёртывание с этими правками даст неработающий вход в панель.
>
> **Что проверено фактически** (`NODE_ENV=production`, запуск из `dist`): панель монтируется без ошибок и без `EACCES`; вход с заданными учётными данными → `302` на `/admin`; вход с `admin@example.com` / `changeme123` → `200`, отказ; неверный пароль при верном пользователе и наоборот — тот же `200`, неразличимо (FR-026); кука при `TRUST_PROXY=true` и `X-Forwarded-Proto: https` → `HttpOnly; Secure; SameSite=Lax` (FR-024).
>
> **Что НЕ проверено**: сборка контейнерного образа. Docker-демон в среде не запущен, поэтому правки `Dockerfile` (копирование компонентов, создание `/app/.adminjs` с правами) остаются **непроверенными**. T058 не закрыт.

## Implementation Strategy

### Минимальный выкатываемый объём

Три истории приоритета P1 — **US1, US2, US3** (T001 — T052). Они закрывают неограниченный расход средств, незащищённую перезапись каталога и работу панели на опубликованных учётных данных. Останавливаться раньше нельзя: US1 без US3 оставляет админку открытой, US3 без US1 оставляет открытым биллинговый эндпоинт.

### Порядок поставки

1. Phase 1 + Phase 2 → механизм ключей готов, существующие тесты зелёные
2. US1 → биллинговый контур закрыт → выкатка в режиме наблюдения
3. US2 → операции записи закрыты
4. US3 → небезопасная конфигурация не стартует → **готово к принудительному режиму**
5. US4, US5 → панель и ошибки (могут идти параллельно с 2–4)
6. US6 → источники и документация
7. T080 → перевод в принудительный режим — завершение выкатки

### Параллельная работа

- Исполнитель A: Phase 1 → Phase 2 → US1 → US2
- Исполнитель B: US4 (панель, требует работы с Docker) → US5
- Исполнитель C: US3 (конфигурация) → US6

US4 и US5 не пересекаются по файлам ни с чем из Foundational — их можно начинать в тот же момент, что и Phase 1.
