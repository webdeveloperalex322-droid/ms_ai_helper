# Quickstart — проверка Production Security Hardening

**Feature**: [spec.md](./spec.md) | **Contracts**: [access-control.md](./contracts/access-control.md), [configuration.md](./contracts/configuration.md)

Сценарии подтверждения работоспособности. Каждый привязан к критерию приёмки спецификации. Реализация здесь не приводится — она в `tasks.md` и в коде.

---

## Предварительные условия

```bash
pnpm install
docker-compose up -d          # Postgres с pgvector на :5432
pnpm db:migrate
pnpm db:seed
```

Локальная альтернатива без Docker — Postgres 18 с собранным pgvector и провайдерами в режиме `mock`.

## Сценарий 1 — автоматические проверки (SC-009)

```bash
pnpm test          # юнит + интеграционные
pnpm test:e2e      # e2e, включая новый обход маршрутов
pnpm lint
pnpm build
```

**Ожидается:** существующие 122 теста проходят без правок их логики, новые проходят, сборка успешна.

**Что это НЕ подтверждает:** ни один из перечисленных прогонов не затрагивает сборку контейнерного образа и запуск панели администратора. Сценарий 5 обязателен отдельно.

## Сценарий 2 — разграничение доступа (SC-001, SC-002)

Запустить с `ACCESS_CONTROL_MODE=enforce`.

| Проверка | Ожидание |
|---|---|
| `POST /v1/assistant/product-answer` без заголовка | `401`, тело по контракту |
| То же с неверным ключом | `401`, **тело побайтово совпадает** с предыдущим (FR-006) |
| То же с действительным клиентским ключом | `200`, ответ прежней формы |
| `POST /v1/import/cities` без ключа | `401`, каталог не изменён |
| `POST /v1/import/cities` с **клиентским** ключом | `401` — клиентский ключ не даёт прав на запись (FR-003) |
| `POST /v1/import/cities` со служебным ключом | `202`, импорт запускается |
| `GET /v1/health` без ключа | `200` (FR-008) |

**Ключевая проверка SC-002:** после серии отклонённых запросов в логе нет ни одного обращения к LLM-провайдеру. Отказ должен происходить до входа в обработчик, а не внутри него.

**Проверка полноты (SC-001):** обойти **весь** перечень маршрутов из [контракта](./contracts/access-control.md#карта-маршрутов-и-требуемого-доступа), а не выборку. Незакрытым останется ровно тот маршрут, который забыли проверить.

## Сценарий 3 — предварительный запрос браузера (edge case, R2)

```bash
curl -i -X OPTIONS http://localhost:3000/v1/assistant/product-answer \
  -H "Origin: <разрешённый источник>" \
  -H "Access-Control-Request-Method: POST"
```

**Ожидается:** успешный ответ с заголовками разрешения, **без предъявления ключа**.

**Почему это критично.** Браузер не передаёт пользовательские заголовки в предварительном запросе. Если он упрётся в проверку ключа, публичный контур перестанет работать из браузера целиком — при том, что все curl-проверки будут проходить. Этот сценарий обязателен до перевода в принудительный режим.

Дополнительно: запрос с источником **вне** списка не должен получать заголовков разрешения (FR-030).

## Сценарий 4 — ограничение частоты (SC-006)

Выполнить `POST /v1/assistant/product-answer` с действительным ключом чаще порога `costly`.

**Ожидается:** избыточные запросы → `429` с заголовком `Retry-After`; платные вызовы для них не выполняются.

**Проверка разделения счётчиков (FR-009c):** параллельно подать запросы со **вторым** клиентским ключом — они должны обслуживаться, пока первый в отказе.

**Проверка `trustProxy` (FR-015):** подать запросы с разными значениями `X-Forwarded-For` и убедиться, что счётчики раздельны. Если они общие — `trustProxy` не включён, и ограничение по источнику неработоспособно за прокси, хотя внешне выглядит рабочим.

## Сценарий 5 — образ и панель администратора (SC-005) **ОБЯЗАТЕЛЬНО**

```bash
pnpm build
docker compose -f docker-compose.prod.yml build app
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml logs -f app
```

| Проверка | Ожидание |
|---|---|
| Старт приложения | Без ошибок; в логе нет сбоя сборки компонентов и нет `EACCES` по `.adminjs` |
| Открытие `/admin` | Форма входа отображается |
| Вход с заданными в `.env.prod` учётными данными | Успешно |
| Вход с `admin@example.com` / `changeme123` | **Отказ** |
| Атрибуты куки `adminjs` | `Secure`, `HttpOnly` |
| Операция чтения в панели | Работает |

**Этот сценарий не заменяется тестами.** Пути компонентов резолвятся в исходное дерево во время выполнения, а `.adminjs/` создаётся при старте — оба обстоятельства проявляются только в собранном образе. Считать задачу выполненной по зелёным тестам нельзя.

## Сценарий 6 — отказ от старта с небезопасной конфигурацией (SC-003)

Для **каждой** переменной из [перечня критичных секретов](./data-model.md#6-перечень-критичных-секретов) поочерёдно:

1. Убрать её из окружения → запуск с `NODE_ENV=production` завершается ненулевым кодом.
2. Задать значением-заглушкой → тот же отказ.
3. Задать значением короче минимума → тот же отказ.

**Проверка формулировки (FR-019):** сообщение называет переменную и характер нарушения; фактического и ожидаемого значений в нём нет.

**Проверка полноты:** при нескольких одновременных нарушениях перечисляются все. Иначе развёртывание превращается в серию перезапусков по одной проблеме за раз.

**Контрольная проверка (FR-020):** с `NODE_ENV=development` и `NODE_ENV=test` приложение по-прежнему стартует без явно заданных секретов.

## Сценарий 7 — ответы об ошибках (SC-004)

Остановить Postgres при работающем приложении, выполнить запрос с действительным ключом.

**Ожидается:** ответ содержит обобщённое сообщение и `requestId`; в теле нет текста исключения драйвера, фрагментов SQL, путей файловой системы и параметров подключения.

**Встречная проверка (FR-028):** по тому же `requestId` в логе присутствует полное сообщение со стеком.

**Проверка неухудшения (FR-029):** запрос с некорректным телом по-прежнему возвращает понятное описание ошибки валидации.

## Сценарий 8 — документация (SC-010, SC-011)

Открыть `/v1/docs` в продакшен-конфигурации.

| Проверка | Ожидание |
|---|---|
| Состав документа | Только клиентский контур и `health` |
| Поиск маршрутов импорта и управления подсказками | Отсутствуют (FR-033) |
| Кнопка авторизации | Присутствует, принимает ключ (FR-034) |
| Пробный запрос с подставленным ключом | Проходит |
| Примеры | Нет действительных ключей и идентификаторов реальных торговых сетей (FR-035) |
| То же в режиме разработки | Документ полный, включая служебные маршруты (FR-036) |

**SC-011 по существу:** сторонний разработчик, располагая только ключом и адресом документации, выполняет успешный запрос без обращения к команде.

## Сценарий 9 — ротация ключа LLM-провайдера (SC-008)

После замены ключа выполнить контрольное обращение к провайдеру **со старым** значением.

**Ожидается:** провайдер отказывает.

Наличие нового ключа в конфигурации не подтверждает отзыв старого — это разные факты, и проверять нужно именно второй.

## Сценарий 10 — переход из режима наблюдения (SC-001a)

1. Развернуть с `ACCESS_CONTROL_MODE=observe`. Запросы без ключа обслуживаются и попадают в лог как подлежащие отклонению.
2. По журналу убедиться, что необновлённых потребителей не осталось.
3. Переключить на `enforce`, перезапустить.

**Ожидается:** переключение выполняется изменением конфигурации и перезапуском, без пересборки образа.

**Условие завершения выкатки:** пока действует режим наблюдения, публичный контур фактически открыт и защищён только ограничением частоты. Выкатка не считается завершённой до перевода в `enforce`.
