# Feature Specification: Разрешение категории товара при подборе

**Feature Branch**: `010-fix-category-filter`

**Created**: 2026-10-01

**Status**: Draft

**Input**: User description: "Фильтр по категории не работает на реальном каталоге: слот category от LLM ('roll','set') сравнивается напрямую с products.category_id, где лежат id категорий venus API. Нужно резолвить категорию из таблицы categories (slug/category_id/name) и отдавать LLM реальный список категорий для rn/target."

## Контекст проблемы

На проде (реальный каталог) любой вопрос, где ассистент распознаёт категорию («роллы», «сет»), возвращает ответ «Не нашёл подходящих товаров (из категории roll) в вашем городе», хотя товары этой категории в городе есть. Вопросы без категории («что есть с лососем») отвечаются нормально, карточки приходят.

Причина: распознанное название категории — короткое служебное слово из фиксированного списка, а в карточке товара хранится идентификатор категории поставщика каталога. Сравниваются они напрямую, совпадений нет никогда. Справочник категорий, который связывает одно с другим, при подборе не используется. На тестовых данных ошибка не видна, потому что там оба значения совпадают.

Затронуты оба пути: ответ на свободный вопрос и показ готовых подсказок (пресетов) — пресеты с категорией отфильтровываются как «нет товаров» и не показываются пользователю.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Вопрос с категорией возвращает товары (Priority: P1)

Пользователь спрашивает «какие у вас есть роллы» или «подбери сет на компанию». Ассистент показывает карточки товаров именно этой категории из каталога его города.

**Why this priority**: Это основной сломанный сценарий — сейчас пользователь всегда получает отказ. Самая частая формулировка вопроса в меню доставки содержит категорию.

**Independent Test**: Задать боевому ассистенту вопрос с названием категории для города с непустым каталогом и проверить, что пришли карточки и все они из запрошенной категории.

**Acceptance Scenarios**:

1. **Given** в городе есть активные товары категории «роллы», **When** пользователь спрашивает «какие у вас есть роллы», **Then** ассистент возвращает непустой список карточек, и каждая карточка — товар категории «роллы».
2. **Given** в городе есть активные сеты, **When** пользователь просит «подбери сет на компанию», **Then** ассистент возвращает карточки сетов, а не произвольных товаров.
3. **Given** категория распознана, **When** пользователь дополнительно задаёт бюджет («роллы до 500 рублей»), **Then** возвращаются только товары этой категории в пределах бюджета.
4. **Given** в городе нет ни одного доступного товара запрошенной категории, **When** пользователь спрашивает про неё, **Then** ассистент возвращает понятный отказ с предложением альтернатив (текущее поведение сохраняется).

---

### User Story 2 - Подсказки с категорией снова показываются (Priority: P2)

Пользователь открывает чат и видит набор готовых подсказок. Подсказки, привязанные к категории («Популярные роллы», «Подобрать сет»), показываются, если товары такой категории в городе действительно есть, и нажатие на них даёт карточки.

**Why this priority**: Подсказки — основная точка входа в диалог, но без них чат остаётся работоспособным, поэтому ниже P1.

**Independent Test**: Запросить список подсказок для города с непустым каталогом и убедиться, что подсказки с категорией присутствуют; нажать такую подсказку и получить карточки.

**Acceptance Scenarios**:

1. **Given** в городе есть роллы, **When** запрашивается список подсказок, **Then** подсказка с категорией «роллы» присутствует в списке.
2. **Given** подсказка с категорией показана, **When** пользователь её выбирает, **Then** возвращаются карточки товаров этой категории.
3. **Given** в городе нет товаров категории подсказки, **When** запрашивается список подсказок, **Then** эта подсказка скрыта (текущее поведение сохраняется).

---

### User Story 3 - Ассистент оперирует реальными категориями каталога (Priority: P3)

Ассистент распознаёт категории, которые реально существуют в каталоге конкретной сети и канала, а не фиксированный зашитый список из шести значений. Если в каталоге появилась новая категория (например, «горячие блюда» или «напитки»), вопросы про неё начинают работать без правок кода.

**Why this priority**: Повышает полноту ответов и убирает ручную синхронизацию списка, но P1/P2 работают и с распознаванием по старому списку.

**Independent Test**: Задать вопрос про категорию, которой нет в прежнем зашитом списке, но которая есть в каталоге города, и получить карточки этой категории.

**Acceptance Scenarios**:

1. **Given** в каталоге города есть категория, отсутствующая в прежнем фиксированном списке, **When** пользователь спрашивает про неё своими словами, **Then** ассистент возвращает товары этой категории.
2. **Given** справочник категорий для города недоступен, **When** пользователь задаёт любой вопрос, **Then** ассистент отвечает как раньше (деградация без ошибки для пользователя).

---

### Edge Cases

- Распознанное название категории не соответствует ни одной категории каталога (опечатка, выдуманная категория) → подбор выполняется без ограничения по категории, пользователь получает релевантные товары, а не отказ.
- Одно название соответствует нескольким категориям каталога (например, «роллы» и «премиальные роллы») → учитываются товары всех совпавших категорий.
- Категория есть в справочнике, но все её товары недоступны/скрыты → отказ с предложением альтернатив, как и раньше.
- Справочник категорий пуст для сети/канала (импорт не выполнялся) → поведение как при неизвестной категории: подбор без ограничения по категории.
- Разные города одной сети используют общий справочник категорий — разрешение не должно зависеть от конкретного города.
- Регистр и лишние пробелы в распознанном названии не влияют на совпадение.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST сопоставлять распознанное название категории со справочником категорий сети и канала и использовать для отбора товаров идентификаторы категорий из этого справочника.
- **FR-002**: Сопоставление MUST срабатывать по любому из признаков категории в справочнике: служебному короткому имени, идентификатору поставщика каталога, отображаемому названию. Сравнение MUST быть нечувствительно к регистру и обрамляющим пробелам.
- **FR-003**: Система MUST поддерживать набор исторических служебных названий (`roll`, `set`, `drink`, `sauce`, `dessert`, `hot`), которые уже сохранены в готовых подсказках, и сопоставлять их с соответствующими категориями реального каталога.
- **FR-004**: Если название категории совпало с несколькими категориями справочника, система MUST отбирать товары всех совпавших категорий.
- **FR-005**: Если название категории не совпало ни с одной категорией справочника, система MUST выполнить подбор без ограничения по категории вместо возврата пустого результата.
- **FR-006**: Отбор по категории MUST применяться одинаково в ответе на свободный вопрос, в ответе на готовую подсказку и в проверке «есть ли товары» при показе списка подсказок.
- **FR-007**: Система MUST передавать распознавателю намерений перечень категорий, реально присутствующих в каталоге запрошенной сети и канала, вместо фиксированного зашитого списка.
- **FR-008**: При недоступности справочника категорий система MUST продолжать отвечать пользователю, используя исторический фиксированный список, и не возвращать ошибку.
- **FR-009**: Прочие ограничения подбора (бюджет, ингредиенты, исключения, острота, доступность товара) MUST продолжать работать совместно с ограничением по категории.
- **FR-010**: Отказ «не нашёл товаров» MUST показываться только когда товаров действительно нет, и MUST называть категорию так, как её видит пользователь (отображаемое название), а не служебным кодом.

### Key Entities

- **Категория каталога**: запись справочника для сети и канала; несёт служебное короткое имя, идентификатор поставщика каталога, отображаемое название, признак активности.
- **Товар**: карточка меню; ссылается на категорию идентификатором поставщика каталога.
- **Распознанное намерение**: результат разбора вопроса пользователя; среди прочего содержит название категории, которое требуется сопоставить со справочником.
- **Готовая подсказка (пресет)**: заранее заданный запрос с зафиксированным названием категории.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Вопросы с упоминанием категории в городе с непустым каталогом возвращают карточки не реже, чем вопросы без категории (сейчас — 0% против 100%).
- **SC-002**: 100% карточек в ответе на вопрос с категорией принадлежат запрошенной категории.
- **SC-003**: Все готовые подсказки с категорией, для которых в городе есть товары, показываются в списке подсказок.
- **SC-004**: Доля ответов «не нашёл подходящих товаров» на боевом трафике снижается до уровня, объяснимого реально пустыми выборками (отказ только при фактическом отсутствии товаров).
- **SC-005**: Время ответа ассистента не ухудшается более чем на 10% относительно текущего.
- **SC-006**: Добавление новой категории в каталог не требует изменения кода для того, чтобы вопросы про неё работали.

## Assumptions

- Справочник категорий заполняется существующим импортом каталога и содержит связь между служебным коротким именем, идентификатором поставщика и отображаемым названием.
- Справочник категорий общий для городов одной сети и канала; разрешение названия выполняется на уровне сети и канала.
- Исторические служебные названия в готовых подсказках остаются в данных как есть; их переназначение выполняется сопоставлением, а не миграцией данных.
- Поведение отказа при реально пустой выборке остаётся прежним и в объём работ не входит.
- Изменения в импорте каталога, схеме хранения товаров и переиндексация поиска не требуются.
- Проверка результата выполняется на боевом стенде на реальных данных, так как на тестовых данных дефект не воспроизводится.
