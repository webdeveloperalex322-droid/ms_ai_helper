# Research: Разрешение категории товара при подборе

**Date**: 2026-10-01 | **Plan**: [plan.md](./plan.md)

## Исходные наблюдения (боевой стенд, 2026-10-01)

Запросы через test-chat к `POST /v1/assistant/product-answer`, `rn=A79C5050-…`, `br=b8b3d1ac-…`, `target=WEB`:

| Сообщение | Результат |
|-----------|-----------|
| «что есть с лососем» | 5 карточек |
| «какие у вас есть роллы» | 0 карточек, `(из категории roll)` |
| «Популярные роллы» | 0 карточек, `(из категории roll)` |
| «подбери сет на компанию» | 0 карточек, `(из категории set)` |

Вывод: каталог, эмбеддинги, LLM и ключи на проде исправны; ломается только ветка с заполненным слотом `category`.

Цепочка: `IntentSlotParserService` (`knownCategories: ['roll','set','drink','sauce','dessert','hot']`) → `ShortlistBuilderService` (`categoryId: slots.category`) → `CatalogService.findByCity` (`eq(products.categoryId, filters.categoryId)`). В `products.category_id` при `CATALOG_API_MODE=real` пишется `raw.categoryId` поставщика (`ProductImportService.upsertProduct` → нормализатор). Совпадение невозможно. Сид-данные (`seeds/test-products.seed.ts`) кладут `categoryId: 'roll'/'set'`, поэтому локально и в тестах дефект не виден.

Таблица `categories` (поля `category_id`, `slug`, `name`, уникальность по `rn+target+slug`) заполняется `CategoryImportService`, но в поиске не используется нигде — grep по `src/modules` показывает её только в `catalog-import` и `admin`.

## Решение 1: где выполнять резолв

**Decision**: отдельный `CategoryResolverService` в `CatalogModule`.

**Rationale**: справочник нужен трём потребителям (подбор шортлиста, гейтинг пресетов, список категорий для LLM); `CatalogModule` уже импортируется и в `AssistantModule`, и в `SuggestionsModule`. Отдельный сервис позволяет кэшировать справочник в одном месте и тестировать сопоставление изолированно.

**Alternatives considered**:
- Резолв внутри `CatalogService.findByCity` — скрытая магия в SQL-слое, нельзя переиспользовать для `knownCategories`, труднее тестировать.
- JOIN с `categories` прямо в запросе — завязывает сопоставление на SQL, нет многоступенчатой стратегии и синонимов, нет кэша.

## Решение 2: стратегия сопоставления

**Decision**: нормализация (нижний регистр, обрезка пробелов, схлопывание небуквенно-цифровых символов) + два уровня: точное/словоформенное совпадение → вхождение подстроки. Берётся первый непустой уровень. Сопоставление идёт по `slug`, `category_id` и `name` категории, по отдельным словам `slug`/`name`, а также по таблице синонимов для исторических слагов.

Уточнено при реализации: отдельный уровень «префикс» выброшен — сравнение по словам покрывает его случаи («роллы» → «Роллы классические») и дополнительно даёт нужное поведение «роллы» → «Премиальные роллы», которого строгий префикс не давал.

**Rationale**: реальные слаги боевого справочника заранее неизвестны (доступ к боевой БД не подтверждён), поэтому стратегия не должна зависеть от их конкретных значений. Уровни упорядочены по убыванию строгости, что делает результат детерминированным и защищает от ложных срабатываний подстроки (она применяется, только если более строгие уровни пусты).

**Alternatives considered**:
- Только точное совпадение по `slug` — ломается, если поставщик называет категорию `rolly`/`роллы`.
- Нечёткое сравнение (расстояние Левенштейна) — недетерминированный порог, лишняя зависимость, сложнее тестировать.
- Только префиксное сравнение без разбора на слова — не находит категорию, стоящую второй в названии («Премиальные роллы»).
- Миграция данных пресетов на реальные `category_id` — ломается при переимпорте каталога и не решает путь свободного вопроса.

## Решение 3: исторические слаги пресетов

**Decision**: таблица синонимов `roll → [roll, rolls, ролл, роллы]`, `set → [set, sets, сет, сеты]`, `drink → [drink, drinks, напиток, напитки]`, `sauce → [sauce, sauces, соус, соусы]`, `dessert → [dessert, desserts, десерт, десерты]`, `hot → [hot, горячее, горячие, горячие блюда]`. Синонимы прогоняются через ту же многоступенчатую стратегию.

**Rationale**: в `seeds/suggestions.seed.ts` слоты пресетов уже сохранены как `roll`/`set`; данные в БД прода трогать не нужно (FR-003). Добавление синонима — правка данных-константы, а не логики.

**Alternatives considered**: переписать пресеты под реальные id — завязка на конкретный импорт, ломается при смене каталога.

## Решение 4: поведение при непопадании

**Decision**: категория не распознана → фильтр по категории не применяется, подбор идёт по остальным ограничениям и по тексту запроса.

**Rationale**: FR-005. Текущее поведение (пустой результат) хуже любого из вариантов: пользователь получает отказ при полном каталоге. Текст запроса всё равно содержит слово «роллы», поэтому гибридный поиск отранжирует нужные товары.

**Alternatives considered**: оставлять жёсткий фильтр и возвращать отказ — это и есть текущий дефект.

## Решение 5: контракт фильтра

**Decision**: `CatalogFilters.categoryId?: string` → `CatalogFilters.categoryIds?: string[]`, в SQL `inArray(products.categoryId, ids)`; бонус скоринга в `HybridRetrieverService.computeScore` переходит на `includes`.

**Rationale**: одна категория-слот может соответствовать нескольким категориям каталога (FR-004). Поле во множественном числе делает это явным и исключает повторное появление старого бага (строка-слаг больше не является валидным значением фильтра по типу).

**Alternatives considered**: оставить `categoryId` и передавать первый найденный id — теряются товары остальных совпавших категорий.

## Решение 6: список категорий для распознавателя

**Decision**: `IntentSlotParserService.parse` принимает `rn`/`target` и запрашивает у резолвера список `{slug, name}` активных категорий; при пустом/ошибочном ответе используется исторический список из шести слагов. Передаваемый в LLM список ограничен сверху (≈40 позиций).

**Rationale**: FR-007 + SC-006: новая категория в каталоге начинает работать без правок кода. Ограничение размера защищает промпт от разрастания.

**Alternatives considered**: оставить зашитый список — нарушает SC-006 и оставляет часть каталога недостижимой для вопросов.

## Решение 7: кэширование

**Decision**: in-memory `Map` по ключу `rn|target`, TTL 5 минут, без внешних зависимостей.

**Rationale**: справочник меняется только при импорте каталога (редко), а читается на каждый запрос ассистента дважды (knownCategories + резолв). TTL 5 минут даёт потолок задержки распространения после импорта и сохраняет SC-005.

**Alternatives considered**:
- Без кэша — +2 SQL на запрос; при текущих 2–6 с ответа некритично, но бессмысленно.
- Инвалидация из импорта — лишняя связность модулей ради редкого выигрыша.

## Открытый вопрос (не блокирующий)

Реальные значения `slug`/`name` в боевой таблице `categories` не просматривались: два read-only `psql`-запроса по ssh были отклонены классификатором auto-mode. Решение спроектировано независимым от них; фактическая проверка — по [quickstart.md](./quickstart.md) на боевом стенде после выката. Если ни один синоним не совпадёт, правка сводится к расширению таблицы синонимов.
