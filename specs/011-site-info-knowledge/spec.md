# Feature Specification: База знаний по информационным страницам сайта

**Feature Branch**: `011-site-info-knowledge`

**Created**: 2026-10-02

**Status**: Draft

**Input**: User description: "Пройтись по информационным страницам сайта https://tyumen.sushi-master.ru/, собрать информацию, векторизировать и сохранить её для получения ответов на вопросы пользователя."

## Контекст

Ассистент сегодня отвечает только на вопросы о товарах меню. Любой вопрос про доставку, оплату, бонусы, акции, адреса ресторанов или компанию распознаётся как «неподдерживаемый» и получает заготовленный отказ: «Я пока помогаю только с вопросами по товарам из нашего меню». При этом ответы на все эти вопросы уже опубликованы на информационных страницах сайта сети — отдельный сайт на каждый город (поддомен вида `tyumen.sushi-master.ru`).

Обследование сайта (2026-10-01/02) показало:

- Информационные страницы одного города: «О компании» (`/about`), «Доставка и оплата» (`/delivery`), «Бонусная программа» (`/bonus`), «Акции» (`/promotions`, плюс страница каждой акции), «Наши рестораны» (`/our-restourants`), «LLM info» (`/llm-info` — специально подготовленный сетью текст о бренде для ИИ-систем), юридические документы (`/public-oferta`, `/privacy`, `/personal-data-processing`, `/personal-data-transfer`). Главная страница и страницы меню — товарные, в объём не входят.
- Текст страниц в HTML-ответе сервера **отсутствует**: сайт — клиентское приложение, содержимое появляется только после выполнения скриптов в браузере. Простая загрузка страницы даёт лишь заголовок и мета-описание. Проверенный рабочий способ получить текст — отрисовать страницу в безголовом браузере и снять итоговый DOM.
- Часть данных доступна и напрямую (список ресторанов, зоны доставки, словари интерфейса), но единого машинного источника для всех страниц нет; акции и юридические документы получить без браузера не удалось.
- Сайт отвечает медленно (десятки секунд на страницу, иногда более минуты), ответы бэкенда периодически обрываются.
- Содержимое разделяется на общее для сети (о компании, бонусы, LLM info, юридические документы) и зависящее от города (адреса и часы ресторанов, условия доставки, набор акций).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Ответ на вопрос о сервисе из знаний сайта (Priority: P1)

Пользователь в чате ассистента спрашивает «сколько стоит доставка», «как можно оплатить заказ», «сколько бонусов начисляется», «какие сейчас акции», «где находятся ваши рестораны», «до скольки работаете». Ассистент отвечает по существу, опираясь на тексты информационных страниц сайта его города, и даёт ссылку на страницу-источник.

**Why this priority**: Сейчас это самый частый класс вопросов, на который ассистент отвечает отказом. Без него база знаний бесполезна.

**Independent Test**: Задать ассистенту для города с загруженной базой знаний вопрос «как оплатить заказ» и получить ответ, содержащий способы оплаты со страницы «Доставка и оплата», и ссылку на эту страницу.

**Acceptance Scenarios**:

1. **Given** база знаний города загружена, **When** пользователь спрашивает «какие способы оплаты есть», **Then** ответ перечисляет способы оплаты, указанные на странице «Доставка и оплата», и содержит ссылку на неё.
2. **Given** база знаний города загружена, **When** пользователь спрашивает «какой кешбэк начисляется», **Then** ответ содержит условия бонусной программы (размер начисления, срок действия баллов, доля оплаты баллами) со страницы «Бонусная программа».
3. **Given** база знаний города загружена, **When** пользователь спрашивает «адрес ближайшего ресторана на Республики», **Then** ответ содержит адрес и часы работы ресторана с страницы «Наши рестораны», подходящего под запрос.
4. **Given** база знаний города загружена, **When** пользователь спрашивает «какие акции сейчас», **Then** ответ перечисляет актуальные акции со страницы «Акции» и ссылается на неё.
5. **Given** вопрос касается сервиса, но ответа на страницах нет (например, «можно ли оплатить криптовалютой»), **When** пользователь его задаёт, **Then** ассистент честно сообщает, что на сайте такой информации нет, предлагает ссылку на ближайшую по теме страницу и/или телефон поддержки, и не выдумывает ответ.
6. **Given** база знаний для города не загружена, **When** пользователь задаёт вопрос о сервисе, **Then** ассистент отвечает текущим отказом «помогаю только с товарами» (деградация без ошибки).
7. **Given** пользователь задаёт товарный вопрос («подбери сет на двоих»), **When** база знаний загружена, **Then** поведение товарного сценария не меняется: карточки товаров приходят как раньше.

### User Story 2 - Сбор и обновление знаний оператором (Priority: P1)

Оператор запускает сбор информационных страниц для города одной командой, получает читаемый снимок собранных текстов (файл в репозитории), проверяет его глазами и загружает в базу ассистента, где тексты индексируются для поиска. Повторный запуск обновляет только изменившиеся страницы.

**Why this priority**: Без наполнения базы знаний сценарий 1 не работает; снимок в репозитории даёт обозримость и позволяет загрузить знания на боевой стенд, где браузера нет.

**Independent Test**: Выполнить сбор для Тюмени, убедиться, что снимок содержит тексты всех целевых страниц (включая адреса ресторанов и список акций), затем выполнить загрузку и убедиться, что страницы и их фрагменты появились в базе со статусом «проиндексировано».

**Acceptance Scenarios**:

1. **Given** указан адрес сайта города и идентификаторы сети/города, **When** оператор запускает сбор, **Then** в снимке появляются записи для каждой целевой страницы с адресом, заголовком, текстом и временем сбора; страницы без текста помечаются как неудачные с причиной, но не останавливают сбор.
2. **Given** снимок собран, **When** оператор запускает загрузку снимка, **Then** страницы сохраняются в базе с привязкой к сети, городу и адресу страницы, нарезаются на фрагменты и индексируются; отчёт показывает число загруженных, обновлённых, пропущенных и неудачных страниц.
3. **Given** снимок загружен ранее и текст страницы не изменился, **When** оператор повторяет загрузку, **Then** эта страница пропускается без повторной индексации.
4. **Given** текст страницы изменился, **When** оператор повторяет загрузку, **Then** старые фрагменты страницы заменяются новыми и переиндексируются.
5. **Given** сайт отвечает медленно или одна страница не открылась, **When** идёт сбор, **Then** остальные страницы собираются, отчёт называет неудачные.
6. **Given** на боевом стенде нет браузера, **When** оператор переносит снимок на стенд и запускает загрузку, **Then** база знаний наполняется без обращения к сайту.

### User Story 3 - Готовые подсказки по сервисным темам (Priority: P3)

Администратор заводит готовую подсказку (пресет) с сервисной темой — «Условия доставки», «Бонусная программа», «Адреса ресторанов». Нажатие на такую подсказку даёт ответ из базы знаний.

**Why this priority**: Удобная точка входа, но P1 работает и без неё.

**Independent Test**: Создать пресет с сервисным намерением и текстом запроса «условия доставки», нажать его в чате, получить ответ со страницы «Доставка и оплата».

**Acceptance Scenarios**:

1. **Given** пресет с сервисным намерением включён для города, **When** пользователь выбирает его, **Then** ассистент отвечает из базы знаний, как на свободный вопрос с тем же текстом.
2. **Given** база знаний города не загружена, **When** пользователь выбирает такой пресет, **Then** возвращается запасной текст пресета или общий отказ, а не ошибка.

---

### Edge Cases

- Вопрос смешанный — о товаре и сервисе одновременно («сколько стоит Филадельфия и доставка») → распознаётся как товарный, если упомянут товар; сервисная часть не обрабатывается в этой версии (ограничение зафиксировано в допущениях).
- Вопрос о конкретном заказе («где мой заказ №123») → остаётся неподдерживаемым: персональных данных в базе знаний нет и быть не должно.
- Вопрос о другом городе («доставляете ли в Москву») → ответ строится по знаниям текущего города; ассистент может сказать, что отвечает за свой город.
- Длинные юридические документы → нарезаются на фрагменты так, чтобы в ответ попадал релевантный раздел, а не весь документ.
- В ответе модели оказалась информация, отсутствующая во фрагментах (галлюцинация) → требование к ответу: опираться только на переданные фрагменты; при сомнении — отправлять к странице-источнику.
- Срабатывание запрета на темы «доставка/оплата/бонусы» в существующей проверке товарных ответов → к сервисным ответам этот запрет не применяется, применяются только запреты на медицинские гарантии и административно заданные фразы.
- Генерация ответа не уложилась во время → запасной ответ: краткая выжимка самого релевантного фрагмента и ссылка на страницу.
- В снимке страница с текстом короче порога (пустой каркас, «страница не найдена») → считается неудачной, в базу не попадает, прежняя версия в базе сохраняется.
- Одна и та же общая страница сети для нескольких городов → хранится отдельно для каждого города (простота важнее дедупликации при единицах страниц).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST уметь собирать текст информационных страниц сайта города из заданного списка адресов, получая содержимое так, как его видит пользователь в браузере (после выполнения клиентских скриптов).
- **FR-002**: Список целевых страниц по умолчанию MUST включать: «О компании», «Доставка и оплата», «Бонусная программа», «Акции» (включая страницы отдельных акций, обнаруженные на списке акций), «Наши рестораны», «LLM info», «Публичная оферта», «Политика конфиденциальности», «Согласие на обработку персональных данных», «Согласие на обработку данных в маркетинговых целях». Оператор MUST иметь возможность сузить или расширить список.
- **FR-003**: Для каждой собранной страницы система MUST сохранять: адрес, заголовок, очищенный текст с сохранением структуры заголовков и списков, время сбора, признак успешности и причину неудачи.
- **FR-004**: Из собранного текста MUST удаляться навигация, шапка, подвал, служебные элементы и повторяющиеся блоки, не относящиеся к содержимому страницы.
- **FR-005**: Результат сбора MUST сохраняться в виде читаемого снимка-файла, пригодного для просмотра человеком и хранения в репозитории; загрузка в базу MUST выполняться из снимка без обращения к сайту.
- **FR-006**: Страницы MUST храниться в базе с привязкой к сети и городу (rn, br) и к адресу страницы; повторная загрузка той же страницы MUST обновлять существующую запись, а не создавать дубликат.
- **FR-007**: Текст страницы MUST нарезаться на фрагменты по смысловым разделам (заголовкам) с ограничением размера фрагмента; каждый фрагмент MUST нести заголовок страницы и раздела для сохранения контекста.
- **FR-008**: Для каждого фрагмента MUST строиться векторное представление тем же поставщиком векторов, что используется для товаров; статус индексации фрагмента MUST быть виден (ожидает / готов / ошибка).
- **FR-009**: Повторная загрузка MUST пропускать страницы, текст которых не изменился и индексация которых уже завершена; при изменении текста старые фрагменты страницы MUST заменяться новыми.
- **FR-010**: Распознавание намерения MUST выделять новый класс «вопрос о сервисе» (доставка, оплата, бонусы, акции, промокоды, адреса и часы работы ресторанов, компания, юридические условия) вместо текущего «неподдерживаемого». Вопросы о конкретном заказе и личном кабинете MUST оставаться неподдерживаемыми.
- **FR-011**: Для вопроса о сервисе система MUST находить наиболее релевантные фрагменты базы знаний города (векторный и ключевой поиск), ограничивая их число, и формировать ответ на русском языке, опираясь только на найденные фрагменты.
- **FR-012**: Ответ на вопрос о сервисе MUST содержать ссылку на страницу-источник наиболее релевантного фрагмента и MUST не содержать карточек товаров.
- **FR-013**: Если релевантных фрагментов нет или база знаний города пуста, система MUST вернуть понятный запасной ответ (текущий отказ либо указание на сайт/поддержку), а не ошибку.
- **FR-014**: Если генерация ответа превысила отведённое время или завершилась ошибкой, система MUST вернуть запасной ответ из текста самого релевантного фрагмента со ссылкой на источник.
- **FR-015**: К ответам о сервисе MUST применяться запреты на медицинские гарантии и административно заданные фразы; запрет на упоминание тем доставки/оплаты/бонусов, действующий для товарных ответов, к ним применяться MUST NOT.
- **FR-016**: Каждый ответ о сервисе MUST записываться в журнал запросов с указанием класса намерения, результата (ответ / пусто / запасной) и адресов использованных страниц.
- **FR-017**: Готовые подсказки MUST поддерживать сервисное намерение: выбор такой подсказки обрабатывается как вопрос о сервисе с текстом запроса из подсказки.
- **FR-018**: Сбор MUST переживать медленные ответы сайта и неудачу отдельных страниц: неудачная страница фиксируется в отчёте, сбор продолжается; отчёт MUST содержать число успешных и неудачных страниц.
- **FR-019**: Снимок для города Тюмень (rn по умолчанию, br Тюмени) MUST быть собран и сохранён в репозитории в рамках этой работы, а база знаний этого города MUST быть загружена и проиндексирована на стенде разработки.

### Key Entities

- **Информационная страница сайта**: единица знаний; принадлежит сети и городу; имеет адрес, заголовок, очищенный текст, отпечаток текста, время сбора, признак активности.
- **Фрагмент страницы**: часть текста страницы с заголовком раздела и порядковым номером; единица индексации и поиска; имеет статус индексации.
- **Векторное представление фрагмента**: вектор для поиска по смыслу; привязан к фрагменту, хранит имя модели и отпечаток текста.
- **Снимок сбора**: файл с результатами одного прохода по сайту города: параметры сбора, список страниц с текстами и статусами.
- **Вопрос о сервисе**: новый класс намерения пользователя; обрабатывается через базу знаний, а не через подбор товаров.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Для города с загруженной базой знаний не менее 90% тестовых вопросов из набора (доставка, оплата, бонусы, акции, адреса, часы работы, о компании — не менее 20 вопросов) получают содержательный ответ со ссылкой на источник вместо отказа.
- **SC-002**: В ответах на тестовый набор отсутствуют факты, которых нет на страницах сайта (проверка вручную по снимку: 0 выявленных выдуманных фактов на 20 вопросов).
- **SC-003**: Сбор страниц Тюмени завершается успешно для 100% страниц из списка по умолчанию при доступном сайте; при недоступности одной страницы остальные собираются.
- **SC-004**: Повторная загрузка неизменённого снимка не выполняет ни одного обращения к поставщику векторов (0 переиндексированных фрагментов).
- **SC-005**: Время ответа на вопрос о сервисе не превышает времени ответа на товарный вопрос более чем на 20% (одинаковое число обращений к модели).
- **SC-006**: Товарные сценарии (существующие автотесты) проходят без изменений.
- **SC-007**: Оператор, следуя документации, собирает и загружает базу знаний нового города без правок кода.

## Assumptions

- Город задаётся оператором явно: адрес сайта города, rn и br. Автоматическое сопоставление поддомена с br в объём не входит.
- Снимок хранится в репозитории как данные (небольшой текстовый файл на город) и обновляется вручную перезапуском сбора; расписание автоматического обновления в объём не входит.
- Сбор выполняется на машине с установленным браузером (рабочая станция оператора или отдельный шаг); на боевом стенде выполняется только загрузка снимка, браузер там не требуется.
- Общие для сети страницы хранятся отдельно для каждого города; дедупликация не требуется при единицах страниц.
- Поставщик векторов и модель — те же, что для товаров; при смене модели база знаний переиндексируется полностью (как и товары).
- Смешанные вопросы (товар + сервис) в этой версии обрабатываются как товарные; одновременный ответ на обе части — отдельная работа.
- Ответ строится по знаниям города из запроса; знания других городов не используются.
- Предварительные проверки «город активен» и «в городе есть товары» остаются общими для всех намерений.
- Отзывы покупателей (`/feedbacks`), страница вакансий и франшизы на внешних сайтах, главная и страницы меню в базу знаний не включаются.
- Юридические документы включаются целиком, нарезка по разделам делает их пригодными для поиска; ответы по ним носят справочный характер и ссылаются на документ.
