# Research: Блокеры продакшен-запуска

**Feature**: [spec.md](./spec.md) | **Date**: 2026-07-30

Неизвестных технологий нет — все решения строятся на уже используемом стеке. Ниже зафиксированы решения по спорным точкам реализации.

## R1. Где живёт продакшен-валидация секретов

**Decision**: Расширить существующую `validateConfig` в `src/config/configuration.ts` блоком, срабатывающим строго при `NODE_ENV === 'production'`. Функция переводится на накопление нарушений: все проверки (zod-ошибки остаются как есть; прикладные — OPENAI_API_KEY при провайдере `openai`, парсинг `CLIENT_API_KEYS`, продакшен-блок) складывают человекочитаемые строки в массив, в конце — один `throw` с полным перечнем.

**Rationale**: `validateConfig` уже вызывается дважды — в `bootstrap()` до создания Nest-приложения ([main.ts:16](../../src/main.ts#L16)) и как фабрика `ConfigModule` — значит, отказ произойдёт до открытия порта в обоих путях. Накопление, а не первый-упавший, требуется FR-005 (007: FR-019).

**Alternatives considered**: Отдельный `production-guard.ts`, вызываемый только из `main.ts` — отклонено: фабрика `ConfigModule` (и тесты, создающие модуль напрямую) обошла бы проверку. `superRefine` внутри zod-схемы — отклонено: проверки зависят от `NODE_ENV` из того же объекта и от производного `clientApiKeys`; вне схемы читается проще и тестируется без zod-обвязки.

## R2. Перечень заглушек: репозиторий содержит больше значений, чем 007 data-model §6

**Decision**: Отвергаемое множество для каждой переменной = дефолт из zod-схемы **плюс все местозаполнители, встречающиеся в файлах окружения репозитория**:

| Переменная | Отвергаемые значения (помимо «не задана» и «короче минимума») |
|---|---|
| `INTERNAL_API_KEY` | `dev-internal-key-change-in-prod` (дефолт схемы), `change-this-in-production` (лежит в `.env.prod` сейчас) |
| `CLIENT_API_KEYS` (каждый ключ) | `dev-client-key-change-in-prod` (из дефолта схемы) |
| `ADMIN_USER` | `admin@example.com` |
| `ADMIN_PASSWORD` | `changeme123` |
| `ADMIN_COOKIE_SECRET` | `dev-cookie-secret-replace-in-prod-!!!` (дефолт схемы), `replace-with-at-least-32-char-random-secret-here` (лежит в `.env.example` сейчас) |

**Rationale**: 007 data-model §6 перечисляет только дефолты схемы, но фактический `.env.prod` содержит `INTERNAL_API_KEY=change-this-in-production` — значение, которого нет в списке 007. Оператор, скопировавший файл, прошёл бы проверку по списку 007 со скомпрометированным (лежащим в git) значением. Проверка длины формально это значение отловит (25 символов < 32), но полагаться на такое совпадение нельзя — достаточно заглушки подлиннее; явный чёрный список надёжнее и даёт осмысленное сообщение «совпадает с заглушкой», а не «короче минимума».

**Alternatives considered**: Только дефолты схемы (как в 007) — отклонено по причине выше. Энтропийная эвристика — отклонено: ложные срабатывания, непрозрачные сообщения.

## R3. Завершение процесса при сбое старта

**Decision**: `bootstrap().catch()` в `src/main.ts`: логирование через `Logger.error` (без Nest-контекста — `console.error` как запасной путь, если логгер недоступен) и `process.exit(1)`.

**Rationale**: Сейчас `bootstrap();` без обработчика — отказ `validateConfig` даёт unhandled rejection; в Node >= 15 это завершает процесс с кодом 1, но с уродливым выводом и без гарантии в будущих рантаймах; оркестратор должен видеть детерминированный ненулевой код (FR-007).

**Alternatives considered**: `process.exitCode = 1` без `exit()` — отклонено: открытые хэндлы (пул Postgres, созданный до сбоя) могут держать процесс живым.

## R4. requestId в теле ответа об ошибке

**Decision**: Фильтр читает `(request as any).requestId`, проставляемый `LoggingInterceptor` ([logging.interceptor.ts:17](../../src/common/interceptors/logging.interceptor.ts#L17)), и добавляет `error.requestId` во **все** ветви ответа. Если идентификатора нет (исключение возникло до интерцептора — например, в гарде), поле опускается; текст остаётся обобщённым.

**Rationale**: Порядок конвейера Nest: гарды → интерцепторы → обработчик. Ошибки гардов (401/403/429) — `HttpException` с безопасными сообщениями, отсутствие requestId там некритично. Внутренние ошибки (FR-010) возникают в обработчиках — интерцептор к этому моменту уже отработал, requestId гарантирован. Это ровно контракт [007 data-model §7](../007-prod-security-hardening/data-model.md#7-errorresponse--тело-ответа-об-ошибке): поле добавляется, существующие не меняются.

**Alternatives considered**: Перенос генерации requestId в Fastify `onRequest`-хук — гарантирует идентификатор во всех ветвях, но трогает жизненный цикл всех запросов ради ветви, где утечки и так нет; отложено (можно сделать в 007/T062 вместе с APP_FILTER). Генерация fallback-UUID в самом фильтре — отклонено: идентификатор, которого нет в логе запросов, вводит оператора в заблуждение.

## R5. Обобщённое сообщение вместо exception.message

**Decision**: В ветви `exception instanceof Error` ([http-exception.filter.ts:50-53](../../src/common/filters/http-exception.filter.ts#L50-L53)) клиентское `message` фиксируется строкой `'Internal server error'`; `exception.message` и стек остаются только в `this.logger.error(...)`, дополненном requestId. Ветви `HttpException` не меняются (FR-012).

**Rationale**: Минимальный дифф, закрывающий утечку (FR-010) с сохранением диагностики (FR-011). Существующий лог уже пишет message+stack — добавляется только requestId для связи с ответом.

**Alternatives considered**: Перерегистрация фильтра как `APP_FILTER` с `ConfigService` и подробностями в dev-режиме (007: T062) — вне объёма, зафиксировано в Assumptions спеки.

## R6. CORS: источник списка и семантика режимов

**Decision**: Новая переменная `CORS_ALLOWED_ORIGINS` (строка, список через запятую, дефолт `''`) в zod-схеме; производное поле `corsAllowedOrigins: string[]` в `AppConfig` — нормализация при разборе: trim, отбрасывание пустых, удаление завершающего `/`, схема и хост в нижний регистр. Поведение:
- продакшен + пустой список → нарушение конфигурации в общем механизме R1;
- продакшен + список → `app.enableCors({ origin: [...corsAllowedOrigins] })`;
- разработка/тест + пустой список → текущее `app.enableCors()` (совместимость с автономным тест-клиентом);
- разработка/тест + непустой список → тот же ограниченный вызов, что и в продакшене (проверяемость до выкатки).

**Rationale**: FR-013/FR-014. Точное сравнение строк-источников — стандартная семантика `origin: string[]` в `@fastify/cors`, на который NestJS делегирует `enableCors`; нормализация на стороне конфигурации устраняет расхождения «домен со слэшем» (edge case спеки).

**Alternatives considered**: Регулярные выражения/маски поддоменов — отклонено: не требуется спекой, расширяет поверхность ошибок. Отдельный Fastify-плагин — отклонено: `enableCors` уже используется, меняется только аргумент.

## R7. Декларативная защита админ-эндпоинтов подсказок

**Decision**: На каждый из трёх обработчиков `SuggestionAdminController` (`findAll`, `create`, `update`) навешивается существующий `@InternalRoute()` ([access-scope.decorator.ts:14](../../src/common/security/access-scope.decorator.ts#L14)); метод `checkAuth`, параметры `@Headers('x-internal-api-key')` и инъекция `ConfigService` удаляются. Глобальный `AccessKeyGuard` уже зарегистрирован как `APP_GUARD` ([app.module.ts:66](../../src/app.module.ts#L66)) и обслуживает scope `internal`.

**Rationale**: FR-015 (007: FR-004). Инфраструктура готова и покрыта тестами (`guard-pipeline.spec.ts`) — работа сводится к замене ручной проверки на метаданные.

**Alternatives considered**: Декоратор на классе контроллера — допустимо и эквивалентно; выбран по-методный вариант для симметрии с остальными контроллерами служебного контура (проверить при реализации; если в `import.controller` принят классовый стиль — унифицировать).

## R8. DTO для create/update подсказок

**Decision**: `CreateSuggestionDto` и `UpdateSuggestionDto` в `src/modules/admin-config/dto/` с `class-validator` + `@nestjs/swagger`. Поля — по колонкам `assistant_suggestions` без `id`/`createdAt`/`updatedAt`: `rn` (UUID), `code`, `title` (строки, обязательные при создании), `emoji?`, `enabled?`, `sortOrder?`, `screenContext?`, `target?`, `activeFrom?`/`activeTo?` (ISO-даты), `allowedBr?` (массив строк), `payload` (вложенный объект — `intent`, `slots`, `retrieval_query`; обязателен при создании), `availabilityRules` (вложенный; обязателен при создании), `fallbackPayload?`. Update — частичная версия (все поля опциональны). Вложенные структуры валидируются `@ValidateNested` + собственными классами; `slots` — с whitelisting известных полей.

**Rationale**: FR-016. Глобальный `ValidationPipe` с `whitelist: true` работает только при типизированном теле; `Omit<NewAssistantSuggestion, ...>` в сервисе задаёт точный контракт.

**Alternatives considered**: `PartialType(CreateSuggestionDto)` из `@nestjs/swagger` для update — принято (меньше дублирования). Zod-схемы вместо class-validator — отклонено: конвенция проекта (CLAUDE.md) — class-validator в DTO, zod только в конфигурации.

## R9. Ротация ключа AITunnel

**Decision**: Ручная операция оператора, кодом не автоматизируется. Последовательность и контрольная проверка — сценарий в [quickstart.md](./quickstart.md): выпуск нового ключа в кабинете AITunnel → обновление `OPENAI_API_KEY` на сервере → отзыв старого → контрольный запрос со старым ключом (ожидается отказ провайдера) → контрольный запрос через приложение (ожидается успех).

**Rationale**: FR-009 (007: FR-022, SC-008). Значение читается из окружения через существующую схему — изменений кода нет.

**Alternatives considered**: Автотест на отзыв — отклонено: требует хранить старый ключ, что противоречит цели отзыва.

## R10. Расположение и форма тестов

**Decision**:
- Юнит-тесты валидации конфигурации: `src/config/tests/configuration.spec.ts` (каталог уже создан, пуст). По каждой переменной перечня — три негативных случая (не задана / заглушка / короче минимума, где применимо), случай нескольких одновременных нарушений, случай отсутствия значений в сообщении, контрольный успешный старт при `NODE_ENV=development` без явных секретов, дубликаты меток/значений `CLIENT_API_KEYS`, пустой `CORS_ALLOWED_ORIGINS` в продакшене.
- Тесты фильтра ошибок: дополнить существующий `src/common/tests/http-exception.filter.spec.ts`.
- Тесты DTO/гарда админ-контроллера: `src/modules/admin-config/tests/` рядом с существующими тестами модуля.

**Rationale**: Конвенция проекта — тесты в `tests/` рядом с кодом модуля; Vitest уже подхватывает `src/**/*.spec.ts`.
