# Feature Specification: Блокеры продакшен-запуска — валидация секретов, утечка ошибок, CORS, админ-контур

**Feature Branch**: `008-prod-launch-blockers`

**Created**: 2026-07-30

**Status**: Draft

**Input**: User description: "Устранение блокеров продакшен-запуска (подмножество спеки 007-prod-security-hardening, задачи T040–T052, T060, T067, T036): (1) production-валидация конфигурации; (2) устранение утечки внутренних ошибок; (3) ограничение CORS; (4) защита админ-контроллера предложений."

Требования 007 (FR-016 — FR-022, FR-027 — FR-031, FR-004, FR-009e) сохраняют силу; здесь они переформулированы как самостоятельные, независимо проверяемые истории. Задачи 007, закрываемые этой спекой: T040–T052, T060–T061, T066–T067, T036–T037.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Отказ старта на небезопасной конфигурации (Priority: P1)

Оператор разворачивает приложение в продакшен-режиме. Если хотя бы один критичный секрет не задан, совпадает с известной заглушкой из репозитория или короче установленного минимума, приложение не начинает обслуживать запросы: старт прерывается с ненулевым кодом завершения и одним сообщением, перечисляющим **все** нарушения — по имени переменной, без вывода значений. Файлы-образцы окружения содержат полный перечень обязательных переменных с заведомо непригодными местозаполнителями, чтобы оператор не мог случайно уехать в прод на дефолтах.

**Why this priority**: Сегодня продакшен способен загрузиться на `changeme123` и `dev-client-key-change-in-prod` — это прямой захват админ-панели и служебного контура любым, кто читал репозиторий. Ни одна другая работа не имеет смысла, пока это возможно.

**Independent Test**: Запуск с `NODE_ENV=production` и по очереди испорченной каждой переменной из перечня — старт падает; запуск в режиме разработки без явных секретов — работает как раньше.

**Acceptance Scenarios**:

1. **Given** продакшен-режим и незаданный `ADMIN_PASSWORD`, **When** приложение стартует, **Then** старт прерывается с ненулевым кодом, сообщение называет `ADMIN_PASSWORD` и характер нарушения, значение не печатается.
2. **Given** продакшен-режим и значение любого секрета, совпадающее с заглушкой из перечня, **When** приложение стартует, **Then** старт прерывается; так для каждой переменной перечня по отдельности.
3. **Given** продакшен-режим и секрет короче минимума (32 символа для машинных значений, 12 для пароля администратора), **When** приложение стартует, **Then** старт прерывается.
4. **Given** продакшен-режим и одновременно три нарушения, **When** приложение стартует, **Then** сообщение перечисляет все три, а не первое найденное.
5. **Given** продакшен-режим и два ключа в перечне клиентских ключей с одинаковой меткой или одинаковым значением, **When** приложение стартует, **Then** старт прерывается.
6. **Given** режим разработки без явно заданных секретов, **When** приложение стартует, **Then** старт успешен на локальных значениях по умолчанию.
7. **Given** любой сбой на этапе инициализации (недоступна база, невалидная конфигурация), **When** процесс завершается, **Then** код завершения ненулевой — без «зависшего» процесса и необработанного отклонения промиса.

### User Story 2 - Ротация скомпрометированного ключа LLM-провайдера (Priority: P1)

Оператор выпускает новый ключ доступа к LLM-провайдеру в личном кабинете, обновляет значение в конфигурации сервера и отзывает прежний ключ. Отзыв подтверждается контрольным обращением со старым ключом, которое провайдер отклоняет.

**Why this priority**: Действующий ключ считается скомпрометированным (попадал в репозиторий). Пока он жив, любой его обладатель расходует оплаченный лимит. Операция ручная и не зависит от кода — блокирует выкатку, а не разработку.

**Independent Test**: Контрольное обращение к провайдеру со старым ключом получает отказ; приложение с новым ключом успешно выполняет запрос.

**Acceptance Scenarios**:

1. **Given** новый ключ выпущен и прописан в конфигурации сервера, **When** прежний ключ отозван в кабинете провайдера, **Then** контрольное обращение со старым ключом отклоняется провайдером.
2. **Given** ротация завершена, **When** приложение обрабатывает запрос, требующий LLM, **Then** запрос выполняется с новым ключом.

### User Story 3 - Внутренние ошибки не утекают клиенту (Priority: P2)

Потребитель API получает при внутреннем сбое (недоступна база, необработанное исключение) обобщённое сообщение и идентификатор запроса — без текста исключения, фрагментов SQL, путей файловой системы и параметров подключения. Оператор по этому идентификатору находит в серверном логе полную запись со стеком. Ожидаемые ошибки уровня приложения — в том числе ошибки валидации входных данных — продолжают возвращать понятное описание.

**Why this priority**: Сейчас тело ответа при не-HttpException содержит исходный `exception.message` — при сбое подключения к базе клиент видит адрес хоста и имя пользователя БД. Утечка происходит сама, без действий злоумышленника.

**Independent Test**: Запрос при остановленной базе возвращает обобщённое тело с идентификатором запроса; запрос с невалидным телом возвращает прежнее описание ошибок валидации.

**Acceptance Scenarios**:

1. **Given** необработанное внутреннее исключение, **When** формируется ответ, **Then** тело содержит обобщённое сообщение и идентификатор запроса и не содержит текста исключения.
2. **Given** тот же сбой, **When** оператор ищет идентификатор запроса в серверном логе, **Then** находит полную запись с исходным сообщением и стеком.
3. **Given** запрос с невалидным телом, **When** срабатывает валидация входных данных, **Then** клиент получает прежнее содержательное описание нарушений.
4. **Given** ожидаемая ошибка уровня приложения (HTTP-исключение с осмысленным статусом), **When** формируется ответ, **Then** её сообщение передаётся клиенту как раньше.

### User Story 4 - Браузерный доступ только с разрешённых источников (Priority: P2)

Оператор задаёт в конфигурации перечень разрешённых источников браузерных запросов. Запрос со стороннего источника не получает заголовков разрешения и блокируется браузером. В продакшен-режиме пустой или незаданный перечень — ошибка конфигурации, прерывающая старт; «разрешить всё» в продакшене невозможно.

**Why this priority**: Сейчас разрешён любой источник — произвольный сайт может выполнять запросы к API из браузера посетителя. Менее опасно, чем P1 (ключи всё равно требуются), но недопустимо для публичного контура.

**Independent Test**: Запрос с источником из перечня получает заголовки разрешения; с источником вне перечня — не получает; продакшен-старт с пустым перечнем падает.

**Acceptance Scenarios**:

1. **Given** перечень источников задан, **When** приходит браузерный запрос с источника из перечня, **Then** ответ содержит заголовки разрешения для этого источника.
2. **Given** перечень источников задан, **When** приходит запрос с источника вне перечня, **Then** заголовки разрешения отсутствуют.
3. **Given** продакшен-режим и пустой перечень, **When** приложение стартует, **Then** старт прерывается с ошибкой конфигурации (в общем сообщении из User Story 1).
4. **Given** режим разработки без заданного перечня, **When** приложение стартует, **Then** локальная разработка и автономный тест-клиент продолжают работать.

---

### User Story 5 - Админ-эндпоинты подсказок защищены декларативно и типизированы (Priority: P2)

Служебные эндпоинты управления подсказками защищаются тем же декларативным механизмом, что и остальной служебный контур, — а не ручной проверкой внутри каждого обработчика. Тела запросов создания и изменения описаны типизированными структурами с проверкой полей: запрос с лишними или невалидными полями отклоняется с описанием нарушений.

**Why this priority**: Ручная проверка держится на дисциплине — один забытый вызов делает маршрут публичным. Нетипизированное тело (`any`) выключает глобальную валидацию: в базу можно записать произвольную структуру.

**Independent Test**: Обращение к каждому эндпоинту подсказок без служебного ключа отклоняется; запрос с невалидным телом отклоняется с перечнем нарушений; корректный сценарий создания/изменения работает как раньше.

**Acceptance Scenarios**:

1. **Given** запрос к любому эндпоинту управления подсказками без служебного ключа, **When** запрос обрабатывается, **Then** доступ отклонён единым механизмом служебного контура.
2. **Given** запрос создания подсказки с полем, отсутствующим в структуре тела, **When** срабатывает валидация, **Then** лишнее поле отброшено либо запрос отклонён согласно глобальной политике валидации.
3. **Given** запрос изменения с полем неверного типа, **When** срабатывает валидация, **Then** клиент получает описание нарушения, запись не изменяется.
4. **Given** корректные запросы создания и изменения со служебным ключом, **When** они обрабатываются, **Then** поведение не отличается от текущего.

---

### Edge Cases

- Несколько нарушений конфигурации одновременно — сообщение перечисляет все (User Story 1, сценарий 4); проверить, что формат остаётся читаемым при 5+ нарушениях.
- Перечень клиентских ключей задан, но каждая запись валидна по отдельности и дублируется по значению — дубликат обнаруживается по значению, не только по метке.
- Перечень источников содержит записи с завершающим слэшем, пробелами или разным регистром схемы — сравнение источников выполняется по нормализованной форме; поведение фиксируется тестом.
- Внутренняя ошибка возникает до того, как запросу присвоен идентификатор — тело ответа всё равно обобщённое; идентификатор допустимо опустить, утечка недопустима.
- Сбой самого механизма логирования при записи полной ошибки — ответ клиенту не меняется и не обогащается деталями.
- Отзыв старого LLM-ключа у провайдера может действовать с задержкой — контрольную проверку выполнять после подтверждения отзыва в кабинете, при необходимости повторить.

## Requirements *(mandatory)*

### Functional Requirements

Нумерация даётся заново; в скобках — соответствие требованиям 007.

- **FR-001**: Система MUST прерывать запуск в продакшен-режиме, если хотя бы один критичный секрет из перечня (клиентские ключи доступа, служебный ключ доступа, учётные данные администратора, секрет подписи сессии) не задан явно (007: FR-016).
- **FR-002**: Система MUST прерывать запуск в продакшен-режиме, если значение критичного секрета совпадает с известным значением-заглушкой, присутствующим в репозитории (007: FR-017).
- **FR-003**: Система MUST прерывать запуск в продакшен-режиме, если значение критичного секрета короче минимума: 32 символа для машинно-генерируемых значений, 12 символов для пароля администратора (007: FR-018).
- **FR-004**: Система MUST прерывать запуск в продакшен-режиме, если два ключа в перечне клиентских ключей совпадают по значению или по метке владельца (007: FR-009e).
- **FR-005**: Сообщение о прерывании запуска MUST собирать **все** обнаруженные нарушения, называть каждую переменную и характер нарушения и MUST NOT выводить фактические или ожидаемые значения (007: FR-019).
- **FR-006**: В режимах разработки и тестирования система MUST сохранять запуск на локальных значениях по умолчанию; значения по умолчанию из схемы конфигурации MUST NOT удаляться (007: FR-020).
- **FR-007**: Любой сбой этапа инициализации MUST завершать процесс с ненулевым кодом; необработанное отклонение промиса при старте недопустимо.
- **FR-008**: Файлы-образцы окружения MUST содержать полный перечень обязательных переменных: образец для разработки — с пояснениями и заведомо непригодными местозаполнителями; файл продакшен-окружения — включая учётные данные администратора и секрет подписи сессии, отсутствующие в нём сейчас.
- **FR-009**: Действующий ключ доступа к LLM-провайдеру MUST быть заменён на новый, прежний — отозван у провайдера до выкатки; отзыв MUST быть подтверждён контрольным обращением со старым ключом, ожидающим отказа (007: FR-022, SC-008).
- **FR-010**: Ответ на внутреннюю ошибку, не являющуюся ожидаемой ошибкой уровня приложения, MUST содержать обобщённое сообщение и идентификатор запроса и MUST NOT содержать исходного текста исключения, фрагментов запросов к базе, путей файловой системы и параметров подключения (007: FR-027).
- **FR-011**: Полное описание ошибки со стеком MUST записываться в серверный лог с тем же идентификатором запроса, что возвращён клиенту (007: FR-028).
- **FR-012**: Ожидаемые ошибки уровня приложения, включая ошибки валидации входных данных, MUST продолжать возвращать клиенту содержательное описание (007: FR-029).
- **FR-013**: Система MUST выдавать браузерные разрешения только источникам из настраиваемого перечня; запросы с источников вне перечня MUST NOT получать заголовков разрешения (007: FR-030).
- **FR-014**: Перечень разрешённых источников MUST задаваться конфигурацией и проверяться на старте; в продакшен-режиме пустой или незаданный перечень MUST прерывать запуск в общем механизме FR-005, разрешение произвольного источника MUST быть невозможно (007: FR-031).
- **FR-015**: Все служебные эндпоинты управления подсказками MUST защищаться единым декларативным механизмом служебного контура; ручная проверка ключа внутри обработчиков MUST быть удалена (007: FR-004).
- **FR-016**: Тела запросов создания и изменения подсказок MUST быть описаны типизированными структурами с проверкой каждого поля, подпадающими под глобальную политику валидации; нетипизированные тела недопустимы.

### Key Entities

- **Критичный секрет**: переменная окружения, компрометация которой открывает доступ к данным или управлению. Перечень, заглушки и минимумы длины — по [007 data-model §6](../007-prod-security-hardening/data-model.md#6-перечень-критичных-секретов): `CLIENT_API_KEYS` (мин. 32 на ключ, в продакшене обязательна), `INTERNAL_API_KEY` (32, заглушка `dev-internal-key-change-in-prod`), `ADMIN_USER` (отличие от `admin@example.com`), `ADMIN_PASSWORD` (12, заглушка `changeme123`), `ADMIN_COOKIE_SECRET` (32, заглушка `dev-cookie-secret-replace-in-prod-!!!`).
- **Перечень разрешённых источников**: настраиваемый список источников браузерных запросов; в продакшене обязателен и непуст; допускает домены сторонних интеграторов.
- **Ответ об ошибке**: структура тела при сбое — обобщённое сообщение, статус, идентификатор запроса; связана с записью в серверном логе тем же идентификатором.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Попытка запуска в продакшен-режиме с любым незаданным, заглушечным или коротким критичным секретом завершается отказом с ненулевым кодом — проверяется отдельно по каждой переменной перечня, по три негативных случая на переменную (не задана / заглушка / короче минимума, где применимо).
- **SC-002**: При нескольких одновременных нарушениях конфигурации сообщение перечисляет 100% обнаруженных нарушений и не содержит ни одного фактического или ожидаемого значения.
- **SC-003**: Запуск в режиме разработки без явно заданных секретов проходит успешно — существующие сценарии разработки и тестов не деградируют (все текущие тесты остаются зелёными).
- **SC-004**: Контрольное обращение к LLM-провайдеру с прежним ключом отклоняется провайдером; обращение с новым ключом выполняется успешно.
- **SC-005**: Ни один ответ об ошибке при недоступности базы данных не содержит маркеров внутренней диагностики (текст исключения, адреса подключения, пути, SQL) — подтверждается проверкой тела ответа; идентификатор из тела находит полную запись в серверном логе.
- **SC-006**: Браузерный запрос с источника вне перечня не получает заголовков разрешения; запуск продакшена с пустым перечнем источников невозможен.
- **SC-007**: 100% эндпоинтов управления подсказками отклоняют обращение без служебного ключа; запрос с невалидным телом отклоняется с описанием нарушений; корректные операции создания и изменения работают без регрессии.

## Assumptions

- Перечень критичных секретов, значений-заглушек и минимумов длины берётся из [007 data-model §6](../007-prod-security-hardening/data-model.md#6-перечень-критичных-секретов) без изменений; новые секреты не добавляются.
- Идентификатор запроса уже проставляется существующим механизмом журналирования запросов; спека требует лишь включить его в тело ответа об ошибке. Возврат расширенных деталей ошибки в режиме разработки (007: T062) — вне объёма: сначала закрыть утечку, удобство отладки — отдельной работой.
- Разделение Swagger-документа по режимам, e2e-обход полной карты маршрутов, HSTS и документация/ADR (007: T033–T035, T038–T039, T053–T059, T063–T079) — вне объёма этой спеки; остаются в 007.
- Ротация LLM-ключа — ручная операция оператора в кабинете провайдера; код меняется только в части того, откуда значение читается (уже реализовано), поэтому история фиксируется контрольным чек-листом, а не автотестом.
- Выкат с режимом наблюдения контроля доступа (007: T080) не входит в объём; порядок выката определяется 007.
- Существующий автономный тест-клиент разработки продолжает работать в режиме разработки без настройки перечня источников.
