# Feature Specification: Расширенный набор подсказок и порционный показ

**Feature Branch**: `012-suggestions-mix`

**Created**: 2026-10-02

**Status**: Draft

**Input**: User description: "Расширение и показ набора готовых подсказок ассистента. Цели: (1) добавить сервисные подсказки (доставка, оплата, бонусы, акции, промокод, адреса и часы работы ресторанов, минимальная сумма заказа), опирающиеся на уже готовое сервисное намерение и базу знаний сайта; (2) добавить товарные подсказки по диете и исключениям (без рыбы, совсем без острого, без огурца, без сливочного сыра, полегче по калориям, веган) и по сценариям (на двоих, обед в офис, большая компания, день рождения, напитки, соусы и допы, запечённые роллы, цена/объём, премиум, с тунцом/угрём); (3) шаблон подсказок «похож на X» не только для Филадельфии (Калифорния, Дракон, Канада); (4) не показывать все подсказки сразу: выдавать ограниченный набор (4-6), смешивая товарные и сервисные, с ротацией и сортировкой по накопленной статистике показов/кликов из suggestion_events; (5) задействовать существующие, но неиспользуемые поля схемы: active_from/active_to (окна по времени суток — обед днём, вечерние сценарии вечером), screen_context (catalog — подбор, cart — апсейл напитков/десертов/соусов/горячего, checkout и пустое состояние — сервисные), allowed_br (акции конкретного города)."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Короткий набор подсказок вместо полного списка (Priority: P1)

Пользователь открывает ассистента в каталоге. Вместо длинного списка всех заготовленных подсказок он видит небольшой набор (4–6 штук), в котором есть и товарные, и сервисные варианты. При повторных заходах набор меняется, поэтому со временем пользователь знакомится с разными возможностями ассистента.

**Why this priority**: Без ограничения и ротации любое расширение каталога подсказок ухудшает экран: пользователь перестаёт читать список. Это предпосылка для остальных историй — реализованная отдельно, она уже улучшает текущий экран с 21 подсказкой.

**Independent Test**: Запросить список подсказок для города с полным каталогом подсказок и убедиться, что вернулось не больше заданного лимита, что состав осмысленно смешан по типам и что разные сессии получают разные наборы при неизменных данных.

**Acceptance Scenarios**:

1. **Given** в сети включено 45 подсказок и лимит экрана равен 6, **When** клиент запрашивает подсказки для города, **Then** возвращается ровно 6 подсказок без повторов.
2. **Given** база знаний города заполнена, **When** клиент запрашивает подсказки для каталога, **Then** в наборе есть минимум одна и максимум две сервисные подсказки, остальные — товарные.
3. **Given** клиент запросил подсказки и получил набор, **When** тот же клиент с тем же идентификатором сессии повторяет запрос, **Then** набор совпадает с предыдущим.
4. **Given** клиент запрашивает подсказки с другим идентификатором сессии, **When** данные в базе не менялись, **Then** набор отличается хотя бы одной подсказкой.

### User Story 2 - Сервисные подсказки о доставке, оплате и бонусах (Priority: P2)

Пользователь, у которого вопрос не про еду, а про сервис («сколько стоит доставка», «как работают бонусы», «какие акции»), видит готовую подсказку с этим вопросом и получает текстовый ответ из базы знаний сайта со ссылкой на страницу-источник, без карточек товаров.

**Why this priority**: Сервисное намерение и база знаний города уже реализованы (фича 011), но попасть в них можно только набрав вопрос руками. Подсказки снимают основную долю вопросов, которые раньше уходили в «не поддерживается».

**Independent Test**: Для города с загруженной базой знаний выбрать сервисную подсказку и убедиться, что пришёл текстовый ответ со ссылкой на источник и без карточек товаров.

**Acceptance Scenarios**:

1. **Given** база знаний города содержит страницу о доставке, **When** пользователь выбирает подсказку «Сколько стоит доставка?», **Then** ассистент отвечает текстом по этой странице и даёт ссылку на неё, карточек товаров в ответе нет.
2. **Given** база знаний города пуста или не проиндексирована, **When** клиент запрашивает список подсказок, **Then** сервисные подсказки в наборе не показываются, а экран заполняется товарными.
3. **Given** база знаний города есть, но релевантных фрагментов по подсказке не нашлось, **When** пользователь выбирает эту подсказку, **Then** он получает понятный запасной ответ, а не ошибку.

---

### User Story 3 - Подсказки по диете, исключениям и сценариям (Priority: P2)

Пользователь с ограничением («не ем рыбу», «без огурца», «совсем не острое») или с поводом («на двоих», «обед в офис», «на день рождения») находит готовую подсказку под свою ситуацию, а не формулирует запрос сам.

**Why this priority**: Это самые частые формулировки живых запросов, которых сейчас нет среди заготовок; дают прирост доли обслуженных запросов без изменения логики подбора.

**Independent Test**: Выбрать каждую новую товарную подсказку в городе с полным меню и убедиться, что вернулись карточки, удовлетворяющие её ограничению.

**Acceptance Scenarios**:

1. **Given** в меню города есть роллы без рыбы, **When** пользователь выбирает подсказку «Без рыбы», **Then** все карточки в ответе не содержат рыбных ингредиентов.
2. **Given** в меню города нет ни одной подходящей позиции под подсказку, **When** клиент запрашивает список подсказок, **Then** эта подсказка в наборе отсутствует.
3. **Given** в меню есть несколько роллов, похожих на «Калифорнию», **When** пользователь выбирает подсказку «Похож на Калифорнию», **Then** в ответе есть похожие роллы и нет самой «Калифорнии».

---

### User Story 4 - Подсказки под экран, время суток и город (Priority: P3)

Набор подсказок соответствует месту и моменту: в корзине предлагаются напитки, десерты, соусы и горячее; на оформлении заказа и на пустом экране — сервисные вопросы; днём — обеденные сценарии, вечером — вечерние; акции конкретного города показываются только в нём.

**Why this priority**: Повышает уместность набора, но требует уже работающего порционного показа (US1) и наполненного каталога (US2, US3).

**Independent Test**: Запросить подсказки для разных экранов, в разное время суток и для разных городов и сравнить составы наборов.

**Acceptance Scenarios**:

1. **Given** пользователь находится в корзине и в городе есть все четыре подсказки-дополнения, **When** клиент запрашивает подсказки для контекста корзины при лимите 6, **Then** не менее 4 мест набора занимают дополнения (напитки, десерты, соусы, горячее).
2. **Given** время обеденное, **When** клиент запрашивает подсказки для каталога, **Then** обеденные сценарии в наборе имеют приоритет над вечерними.
3. **Given** подсказка ограничена одним городом, **When** клиент запрашивает подсказки для другого города, **Then** эта подсказка не показывается.
4. **Given** подсказка настроена на несколько экранов, **When** клиент запрашивает подсказки для любого из них, **Then** подсказка доступна в каждом из этих контекстов.

---

### User Story 5 - Порядок по накопленной статистике (Priority: P3)

Подсказки, которые пользователи выбирают чаще, со временем попадают в набор чаще, а бесполезные вытесняются — без ручной перестановки порядка администратором.

**Why this priority**: Даёт самонастройку экрана, но бессмысленна до того, как в базе накопятся события показов и кликов.

**Independent Test**: Подготовить набор событий показов и кликов с разным соотношением и убедиться, что подсказки с высокой долей кликов отбираются чаще, а при отсутствии событий порядок совпадает с заданным администратором.

**Acceptance Scenarios**:

1. **Given** у подсказки A доля кликов на показ существенно выше, чем у B, и у обеих достаточно показов, **When** клиент многократно запрашивает подсказки с разными сессиями, **Then** A попадает в наборы чаще B.
2. **Given** событий по подсказкам нет вовсе, **When** клиент запрашивает подсказки, **Then** порядок определяется заданным администратором порядком сортировки.
3. **Given** подсказка добавлена только что и не имеет показов, **When** клиент многократно запрашивает подсказки, **Then** подсказка всё равно попадает в наборы, чтобы набрать статистику.

---

### Edge Cases

- Все подсказки города скрыты проверкой наличия товаров и пустой базой знаний — набор пуст: клиент должен получить пустой список без ошибки, экран подсказок не показывается.
- Подходящих подсказок меньше лимита — возвращается столько, сколько есть, без заполнения непригодными.
- Сервисных подсказок достаточно, а товарных нет (крошечное меню) — квота на сервисные ослабляется, набор заполняется сервисными.
- Запрошен неизвестный контекст экрана — используется набор каталога.
- Идентификатор сессии клиент не передал — набор формируется как для новой сессии, без требования стабильности.
- Сценарий подсказки не попадает ни в одно окно времени суток (или сценария нет вовсе) — подсказка участвует в отборе без штрафа.
- Подсказка выключена или вышла из окна активности между запросом списка и выбором подсказки — выбор обрабатывается запасным ответом, как сейчас для ненайденной подсказки.
- Окно по времени суток пересекает полночь (например, вечерние сценарии с 18:00 до 02:00) — должно работать как непрерывный интервал.
- В одном городе база знаний проиндексирована, в другом — нет: сервисные подсказки показываются только в первом.
- Статистика собрана по одному каналу (WEB), а запрос пришёл из другого (APP) — ранжирование не должно переносить чужую статистику как свою.

## Requirements *(mandatory)*

### Functional Requirements

#### Наполнение каталога подсказок

- **FR-001**: Каталог заготовленных подсказок MUST содержать сервисные подсказки минимум по темам: стоимость доставки, сроки доставки, способы оплаты, бонусная программа, текущие акции, применение промокода, адреса и часы работы ресторанов, минимальная сумма заказа.
- **FR-002**: Сервисная подсказка MUST обрабатываться как вопрос о сервисе: ответ формируется из базы знаний города со ссылкой на источник и без карточек товаров.
- **FR-003**: Каталог MUST содержать товарные подсказки по диете и исключениям: без рыбы, совсем без острого, без огурца, без сливочного сыра, полегче по калориям, вегетарианское/без животных продуктов.
- **FR-004**: Каталог MUST содержать товарные подсказки по сценариям: на двоих, обед в офис, большая компания, день рождения, напитки, соусы и дополнения, запечённые роллы, выгодное соотношение цены и объёма, премиальный выбор, роллы с тунцом и с угрём.
- **FR-005**: Подсказки вида «похож на X» MUST существовать не только для «Филадельфии», но и для «Калифорнии», «Дракона» и «Канады», и MUST исключать из ответа сам товар-образец.
- **FR-006**: Все новые подсказки MUST задаваться так же, как существующие (повторная загрузка данных не создаёт дубликатов и обновляет уже заведённые), и MUST оставаться доступными для правки администратором: заголовок, порядок, включение, контекст экрана, окно активности, города.
- **FR-007**: Каждая подсказка MUST иметь запасной текст и быстрые ответы на случай пустого результата — включая новые сервисные подсказки.

#### Отбор и показ

- **FR-008**: Список подсказок MUST возвращать не больше настраиваемого лимита позиций; лимит по умолчанию — 6.
- **FR-009**: Отбор MUST происходить до применения лимита: лимит отсекает подсказки по итоговому приоритету отбора, а не по случайному порядку выборки из базы.
- **FR-010**: В контексте каталога набор MUST смешивать типы: при наличии доступных сервисных подсказок в наборе их не меньше одной и не больше двух, остальные позиции — товарные.
- **FR-011**: Если подсказок одного типа не хватает, квота MUST ослабляться, а набор — дополняться подсказками другого типа, вместо возврата неполного набора.
- **FR-012**: Набор MUST различаться между сессиями при неизменных данных (ротация) и MUST быть стабильным внутри одной сессии: повторный запрос с тем же идентификатором сессии возвращает тот же состав.
- **FR-012a**: Запрос списка подсказок MUST принимать идентификатор сессии; он служит единицей стабильности и ротации набора. Параметр необязательный: без него набор формируется как для новой сессии и стабильность не гарантируется.
- **FR-013**: Набор MUST не содержать повторов одной подсказки.
- **FR-014**: Пустой набор MUST возвращаться как пустой список без ошибки.

#### Пригодность подсказки

- **FR-015**: Товарная подсказка MUST скрываться, если в городе нет товаров, удовлетворяющих её ограничениям (текущее поведение сохраняется).
- **FR-016**: Пригодность сервисной подсказки MUST проверяться по наличию проиндексированной базы знаний города, а не по наличию товаров; проверка наличия товаров к сервисным подсказкам применяться MUST NOT.
- **FR-017**: Проверка пригодности MUST не превращать отказ в ошибку запроса: при сбое проверки подсказка показывается, как сейчас.

#### Контекст

- **FR-018**: Подсказка MUST поддерживать показ в нескольких контекстах экрана; поддерживаемые контексты: каталог, корзина, оформление заказа, пустое состояние.
- **FR-019**: В контексте корзины подсказки-дополнения (напитки, десерты, соусы и дополнения, горячее) MUST занимать не менее двух третей мест набора, если их достаточно для этого; при нехватке — все доступные.
- **FR-020**: В контексте оформления заказа и пустого состояния сервисные подсказки MUST занимать не менее двух третей мест набора, если их достаточно для этого; при нехватке — все доступные, остальные места отдаются товарным.
- **FR-021**: Время суток MUST определяться на стороне системы и повышать приоритет подсказок соответствующего сценария: обеденные — в обеденное время, вечерние — в вечернее, ночные — ночью. Отдельного поля настройки времени у подсказки не вводится: привязка идёт по сценарию из её полезной нагрузки.
- **FR-021a**: Соответствие «сценарий — часы суток» MUST задаваться настройкой системы, а не быть захардкоженным в одном месте без возможности правки; интервал, пересекающий полночь, MUST обрабатываться как непрерывный.
- **FR-021b**: Подсказка без сценария MUST отбираться независимо от времени суток, без штрафа.
- **FR-021c**: Существующие окна активности (`active_from`/`active_to`) MUST сохранять текущий смысл — разовые периоды показа (например, акция до определённой даты) — и к времени суток отношения не имеют.
- **FR-022**: Ограничение подсказки по городам MUST соблюдаться: подсказка, привязанная к списку городов, в остальных городах не показывается.
- **FR-023**: Неизвестный контекст экрана MUST обрабатываться как контекст каталога.

#### Ранжирование по статистике

- **FR-024**: Приоритет отбора MUST учитывать накопленную долю выборов на показ по каждой подсказке.
- **FR-025**: Статистика MUST считаться по событиям показов и выборов подсказок за ограниченный недавний период и отдельно по каналу запроса.
- **FR-026**: Подсказка с числом показов ниже порога достоверности MUST ранжироваться по заданному администратором порядку, а не по случайной доле выборов на малых числах.
- **FR-027**: При полном отсутствии событий порядок отбора MUST совпадать с заданным администратором порядком сортировки.
- **FR-028**: Новые подсказки без статистики MUST периодически попадать в наборы, чтобы накопить показы.
- **FR-029**: Вычисление статистики MUST не задерживать выдачу списка подсказок сверх заданного бюджета времени и при недоступности статистики MUST деградировать до порядка администратора.

### Key Entities

- **Подсказка**: заготовленный вопрос пользователя. Атрибуты: код, заголовок, тип (товарная / сервисная), включённость, порядок сортировки, контексты экрана, окно активности, список городов, полезная нагрузка (намерение, ограничения подбора, поисковый запрос), правила пригодности, запасной ответ.
- **Событие подсказки**: факт показа или выбора подсказки с привязкой к сети, городу, каналу, сессии и времени. Основа статистики.
- **Статистика подсказки**: производная величина — показы, выборы и их отношение за недавний период в разрезе канала.
- **База знаний города**: проиндексированные фрагменты информационных страниц сайта; определяет пригодность сервисных подсказок и источник их ответов.
- **Окно времени суток**: настраиваемое соответствие сценария подсказки интервалу часов (обед, вечер, ночь), по которому повышается приоритет отбора.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На экране ассистента пользователь видит не более 6 подсказок, и при заполненной базе знаний города среди них есть минимум одна сервисная.
- **SC-002**: Каталог заготовленных подсказок содержит не менее 45 позиций, из них не менее 8 сервисных и не менее 6 по диете и исключениям.
- **SC-003**: Доля запросов, завершившихся запасным ответом «вопрос не поддерживается», снижается минимум на 30% относительно замера до изменения.
- **SC-004**: Ни одна показанная подсказка не ведёт к пустому результату: доля выборов подсказок с пустым ответом не превышает 2%.
- **SC-005**: За сутки работы в наборах появляется не менее 70% включённых подсказок города (ротация покрывает каталог), при этом внутри одной сессии состав не меняется.
- **SC-006**: Список подсказок открывается без заметной задержки: 95% запросов списка укладываются в 0,3 секунды.
- **SC-007**: Доля выборов подсказки на показ набора не ниже текущего уровня при вчетверо меньшем числе показанных подсказок.

## Assumptions

- События показов и выборов подсказок передаёт клиентское приложение через существующий приём событий; на момент запуска истории событий может не быть, поэтому ранжирование обязано корректно работать на пустой статистике.
- Период расчёта статистики — последние 30 дней; порог достоверности — 50 показов подсказки. Значения настраиваемые.
- Контекст корзины не учитывает фактическое содержимое корзины: предлагается статический набор дополнений. Персонализация по составу корзины вне объёма этой работы.
- База знаний информационных страниц собрана и проиндексирована только для части городов (на старте — Тюмень); для остальных городов сервисные подсказки будут скрыты до их загрузки.
- Сервисное намерение, поиск по базе знаний и ответ со ссылкой на источник уже реализованы фичей 011 и переиспользуются без изменений логики ответа.
- Идентификатор сессии для стабильности набора приходит от клиента вместе с запросом списка (тот же идентификатор, что уже передаётся в событиях); клиентское приложение потребует доработки, чтобы начать его присылать. До этого ротация работает, стабильность внутри визита — нет.
- Время суток считается по часовому поясу города; если пояс города неизвестен, используется пояс сервера.
- Окна времени суток по умолчанию: обед 11:00–16:00, вечер 17:00–23:00, ночь 23:00–05:00. Значения настраиваемые.
- Тексты подсказок — на русском языке, с эмодзи в начале заголовка, как в текущем наборе.
- Лимит экрана, период и порог статистики задаются настройками окружения и могут отличаться на стендах.
