# Contract: отбор набора подсказок

**Feature**: 012-suggestions-mix | Внутренний контракт `SuggestionSelectorService` и его зависимостей. Описывает поведение, проверяемое тестами.

## Вход

```text
candidates:   подсказки сети, прошедшие жёсткие фильтры
limit:        размер набора (настройка, по умолчанию 6)
serviceQuota: { min: 1, max: 2 } для контекста catalog; для checkout/empty — профиль «сервисные приоритетны»; для cart — 0
stats:        Map<suggestionId, { shown, clicked }> | пустая
dayPart:      lunch | evening | night | other
context:      catalog | cart | checkout | empty
seed:         строка (session_id или случайная на запрос)
```

## Жёсткие фильтры (до взвешивания)

Подсказка исключается, если верно любое:

1. `enabled = false`.
2. `target` не совпадает с каналом запроса.
3. Контекст запроса отсутствует в `screen_contexts` (при пустом `screen_contexts` — в `screen_context`, при пустом и том — считается `catalog`).
4. `active_from > now` или `active_to < now`.
5. `allowed_br` непустой и не содержит город запроса.
6. Товарная подсказка: товаров города под её слоты меньше `min_products_count` (при `check_products_exist` и включённом `HIDE_EMPTY_SUGGESTIONS`).
7. Сервисная подсказка: у города нет фрагментов базы знаний со статусом `ready`.

Проверка пункта 6 выполняется пакетно с ограничением одновременности и кешем на `rn|br|target`; её сбой трактуется как «товары есть» (FR-017). Сбой пункта 7 трактуется как «базы знаний нет».

## Вес кандидата

```text
base           = 1 / (1 + sort_order / 100)

ctrFactor      = shown >= STATS_MIN_IMPRESSIONS
                   ? 1 + CTR_WEIGHT * (clicked / shown)
                   : 1 + EXPLORATION_BONUS

dayPartFactor  = сценарий подсказки сопоставлен текущей части суток ? DAYPART_BOOST
                 сценарий сопоставлен другой части суток            ? 1 / DAYPART_BOOST
                 иначе                                               1

contextFactor  = подсказка профильна для контекста ? CONTEXT_BOOST : 1

weight         = base * ctrFactor * dayPartFactor * contextFactor
```

Профильность контекста:

| Контекст | Профильные подсказки | Нижняя граница мест (FR-019, FR-020) |
|----------|----------------------|--------------------------------------|
| `catalog` | товарные подборки (без повышения дополнений) | не задана; действует квота сервисных 1–2 |
| `cart` | `drinks`, `dessert`, `sauces_addons`, `hot_food` | `ceil(2/3 * limit)` мест (при лимите 6 — 4), либо все доступные, если их меньше |
| `checkout`, `empty` | сервисные | `ceil(2/3 * limit)` мест, либо все доступные, если их меньше |

Нижняя граница — жёсткое правило, а не следствие множителя: профильные кандидаты отбираются первыми до её выполнения, остаток мест заполняется прочими.

Значения по умолчанию: `CTR_WEIGHT = 2.0`, `EXPLORATION_BONUS = 0.15`, `DAYPART_BOOST = 1.5`, `CONTEXT_BOOST = 2.0`, `STATS_MIN_IMPRESSIONS = 50`, период статистики — 30 дней. Все задаются настройкой окружения.

## Выборка

1. Разделить кандидатов на `service` и `product`.
2. В контекстах `cart`, `checkout`, `empty`: отобрать профильных кандидатов до нижней границы мест (`ceil(2/3 * limit)` или все доступные) взвешенной выборкой без повторов.
3. В контексте `catalog`: отобрать сервисные — `n = clamp(serviceQuota.min, serviceQuota.max, число пригодных сервисных)` позиций тем же способом.
4. Остаток мест заполнить прочими кандидатами тем же способом.
5. Если кандидатов одного типа не хватило — добить недостачу из другого типа (FR-011).
6. Отсортировать объединённый набор по `weight` по убыванию, при равенстве — по `sort_order` по возрастанию.

Взвешенная выборка без повторов: на каждом шаге выбирается кандидат с вероятностью `weight / Σweight` по значению детерминированного генератора; выбранный удаляется из пула.

## Детерминизм

- Генератор — mulberry32, засеянный 32-битным хешем строки `seed | rn | br | target | context`.
- При одинаковых входах (включая `stats` и `dayPart`) результат побитово одинаков — основа теста FR-012.
- Разные `session_id` дают разные наборы при тех же данных — основа теста ротации (SC-005).
- Без `session_id` seed случайный на запрос: набор валиден, стабильность не гарантируется.

## Деградации

| Отказ | Поведение |
|-------|-----------|
| Статистика недоступна или пуста | все `ctrFactor` равны `1 + EXPLORATION_BONUS`; порядок определяется `sort_order` и контекстом (FR-027) |
| Проверка наличия товаров упала | подсказка считается пригодной (FR-017) |
| Проверка базы знаний упала | сервисные подсказки скрываются, набор заполняется товарными |
| Кандидатов меньше лимита | возвращается столько, сколько есть |
| Кандидатов нет | пустой набор |

Ни один отказ не поднимается наружу как ошибка HTTP.

## Проверяемые свойства (для тестов)

1. Длина результата `= min(limit, |candidates|)`.
2. Нет повторов.
3. В `catalog` при наличии ≥1 пригодной сервисной подсказки их в наборе 1–2.
3a. В `cart` при наличии ≥4 пригодных дополнений они занимают ≥4 из 6 мест; в `checkout`/`empty` то же для сервисных.
4. При одинаковом seed два вызова совпадают; при разных — отличаются хотя бы одним элементом (на каталоге ≥ 2×limit).
5. Подсказка с достоверно более высоким CTR попадает в наборы чаще при прогоне на 200 разных seed.
6. Подсказка со сценарием `lunch` попадает чаще в обеденное окно, чем вне него.
7. Подсказка без статистики попадает в наборы при прогоне на 200 seed (исследование не нулевое).
8. Подсказка, не прошедшая жёсткий фильтр, не появляется ни при каком seed.
