# Research: Расширенный набор подсказок и порционный показ

**Feature**: 012-suggestions-mix | **Date**: 2026-10-02

Все открытые вопросы спеки закрыты решением заказчика (см. [checklists/requirements.md](./checklists/requirements.md)); ниже — технические решения по их реализации и по тем местам текущего кода, которые требований спеки не выдерживают.

## R1. Алгоритм отбора набора

**Decision**: взвешенная выборка без повторов с детерминированным генератором, засеянным от `session_id`.

- Вес кандидата: `weight = base * ctrFactor * dayPartFactor * contextFactor`, где `base = 1 / (1 + sort_order/100)` (порядок администратора как априор).
- Отбор: `k` проходов по кандидатам, на каждом — выбор пропорционально весу (roulette wheel) с удалением выбранного. Генератор — mulberry32 от `hash(session_id | rn | br | target | screen_context)`.
- Порядок вывода: по итоговому весу по убыванию, при равенстве — по `sort_order`. Так самое уместное стоит первым, а порядок администратора остаётся значимым.

**Rationale**: один проход, без запросов в БД на кандидата; стабильность внутри сессии получается бесплатно из детерминированного seed; ротация — из разных `session_id`. Квота типов (FR-010) накладывается как два независимых отбора: 1–2 места под сервисные, остальные под товарные.

**Alternatives considered**:
- Чистая сортировка по весу без случайности — ротации нет, пользователь всегда видит одни и те же 6 подсказок (нарушает FR-012, SC-005).
- Epsilon-greedy / Thompson sampling — даёт более честное исследование, но требует хранения состояния и усложняет воспроизводимость в тестах; отложено.
- Хранение выданного набора в БД на сессию — лишняя таблица и запись на каждый показ; детерминированный seed даёт то же без состояния.

**Known limitation**: при переходе через границу части суток (например, 16:00) состав набора у той же сессии может измениться, потому что меняется `dayPartFactor`. Зафиксировано в спеке как краевой случай; стабильность гарантируется в пределах части суток.

## R2. Статистика показов и выборов

**Decision**: агрегат по `assistant_suggestion_events` с кешем в памяти.

- Запрос: `select suggestion_id, count(*) filter (where event_type = 'suggestion_shown') as shown, count(*) filter (where event_type = 'suggestion_clicked') as clicked from assistant_suggestion_events where rn = $1 and target = $2 and created_at > now() - interval '<N> days' group by suggestion_id`.
- Разрез: `rn` + `target`. По `br` не группируем — в одном городе данных не хватит на порог достоверности.
- `ctrFactor = 1 + CTR_WEIGHT * (clicked / shown)` при `shown >= SUGGESTIONS_STATS_MIN_IMPRESSIONS`, иначе `ctrFactor = 1 + EXPLORATION_BONUS` (FR-028: новая подсказка получает небольшой бонус, а не ноль).
- Кеш: `Map<rn|target, {stats, expiresAt}>`, TTL 60 с. Промах кеша — один агрегирующий запрос на город-канал в минуту.
- Сбой или таймаут запроса статистики — пустая статистика, все `ctrFactor` нейтральны (FR-029).

**Rationale**: индекс `idx_suggestion_events_type (event_type, created_at)` уже есть; агрегат по 30 дням на одну сеть — десятки тысяч строк максимум, в кеш попадает один раз в минуту. Укладывается в бюджет 0.3 с (SC-006).

**Alternatives considered**: материализованное представление с периодическим refresh — лишняя миграция и планировщик для объёмов, которые считаются за миллисекунды; счётчики-колонки на подсказке — теряется окно 30 дней и разрез по каналу.

**Note**: события шлёт клиент (`POST /v1/assistant/events`, типы `suggestion_shown` / `suggestion_clicked` уже поддержаны). До доработки клиента статистика пуста — путь «нет данных → порядок администратора» (FR-027) является рабочим, а не теоретическим.

## R3. Несколько контекстов экрана у одной подсказки

**Decision**: добавить `screen_contexts jsonb` (массив строк), оставив существующий `screen_context text` как устаревшее одиночное значение.

- Разрешение: если `screen_contexts` непустой — используется он; иначе — `screen_context`; иначе — `catalog`.
- Допустимые значения: `catalog`, `cart`, `checkout`, `empty`.
- Неизвестный контекст в запросе → трактуется как `catalog` (FR-023).

**Rationale**: подсказки-дополнения (напитки, десерты, соусы, горячее) нужны и в каталоге, и в корзине; сервисные — и на пустом экране, и на оформлении. Дублировать строки на каждый контекст — путь к расхождению заголовков. Новая колонка не ломает ни текущий сид, ни админское API.

**Alternatives considered**: смена типа `screen_context` на массив — требует миграции данных и ломает `CreateSuggestionDto`/`UpdateSuggestionDto`; отдельная таблица связи — избыточно для перечисления из четырёх значений.

## R4. Пригодность сервисной подсказки

**Decision**: отдельная проверка «в городе есть проиндексированная база знаний» вместо проверки наличия товаров.

- Запрос: `exists(select 1 from site_page_chunks where rn = $1 and br = $2 and embedding_status = 'ready' limit 1)`, покрыт индексом `idx_site_page_chunks_rn_br_status`.
- Результат кешируется в памяти с TTL 5 минут на `rn|br` (база знаний меняется только импортом).
- Текущий `checkProductsExist` к подсказкам с `intent = 'info_question'` не применяется вовсе.

**Rationale**: сейчас `SuggestionService.checkProductsExist` прогнал бы сервисную подсказку через `catalogService.findByCity` со пустыми слотами — проверка прошла бы «успешно» по любому товару города и подсказка показывалась бы в городах без базы знаний, где ответом всегда был бы отказ (нарушение FR-016 и SC-004).

**Alternatives considered**: проверять наличие записи в `site_pages` — страница может быть собрана, но не проиндексирована, тогда векторный поиск пуст; проверять по конкретной теме подсказки (есть ли фрагмент про доставку) — потребовало бы поиска на каждую подсказку в списке, дорого; тему оставляем на ответный путь, где уже есть деградация в `not_found`.

## R5. Время суток

**Decision**: часть суток считает сервер и повышает вес подсказки по `payload.slots.scenario`; новых полей у подсказки нет.

- Окна по умолчанию: `lunch 11:00–16:00`, `evening 17:00–23:00`, `night 23:00–05:00`; интервал через полночь нормализуется как два отрезка.
- Карта сценариев: `lunch → lunch`; `dinner`, `evening`, `movie` → `evening`. Сценарий без карты и подсказка без сценария — множитель 1 (FR-021b).
- Внутри своего окна — `dayPartFactor = DAYPART_BOOST` (по умолчанию 1.5), вне окна — `1 / DAYPART_BOOST` (мягкое понижение, не исключение).
- Часовой пояс: конфигурация `SUGGESTIONS_TIMEZONE` (по умолчанию `Asia/Yekaterinburg` — пояс Тюмени, города первого запуска). В `cities` часового пояса нет, поэтому пояс на сеть, а не на город; при появлении поля пояс города вытеснит настройку.
- Окна и карта задаются как JSON в переменной окружения, валидируются Zod-схемой `configuration.ts` со значением по умолчанию.

**Rationale**: `active_from`/`active_to` — абсолютные `timestamp`, повторяющийся дневной интервал ими не выражается; добавлять поле ради трёх окон не требуется, потому что сценарий у подсказки уже есть и несёт тот же смысл. Мягкое понижение вместо исключения сохраняет наполнение набора в городах с малым каталогом.

**Alternatives considered**: новое поле `day_part` у подсказки (вариант A вопроса) — отклонён заказчиком; жёсткая фильтрация по окну — риск пустого набора ночью.

## R6. Идентификатор сессии в запросе списка

**Decision**: необязательный параметр `session_id` у `GET /v1/assistant/suggestions`; при отсутствии — seed из случайного значения на запрос.

- Тот же идентификатор клиент уже передаёт в `POST /v1/assistant/events` и в `product-answer`, отдельной сущности не вводится.
- Формат не валидируется как UUID: клиент может использовать свой идентификатор визита; ограничение — строка до 128 символов.

**Rationale**: без параметра стабильность внутри визита недостижима (сервер не отличает повторный запрос того же пользователя); делать параметр обязательным нельзя — сломает текущих клиентов.

## R7. Данные под новые товарные подсказки

**Decision**: новые подсказки опираются только на уже поддержанные фильтры каталога, кроме одного расширения — верхней границы калорийности.

Поддержано сейчас (`CatalogFilters`): `budgetMax`, `categoryIds`/`categoryNames` (через `CategoryResolverService`, легаси-слаги `roll`, `set`, `drink`, `sauce`, `dessert`, `hot` распознаются), `preferredIngredients`, `excludedIngredients`, `spicy`.

Требует доработки:

1. **`calories_max`** — у `products` есть колонка `calories` (из `nutritional.calorie` провайдера), но фильтра нет. Добавляем `caloriesMax` в `CatalogFilters` и слот `calories_max`. Единица измерения провайдера документально не подтверждена (ккал на порцию либо на 100 г), поэтому порог подсказки «полегче» выносится в значение подсказки, а не в код, и проверяется на боевых данных Тюмени при реализации; при пустом результате подсказка просто скрывается правилом `hide_if_empty`.
2. **`excluded_product_names`** — слот существует, но влияет только на промпт модели: детерминированного отсечения товара-образца нет. Для подсказок «похож на X» (FR-005, сценарий US3.3) добавляем отсечение по имени товара на этапе формирования шортлиста, чтобы «Калифорния» не попадала в ответ «похож на Калифорнию» независимо от поведения модели.

Не требует доработки: `people_count`, `scenario`, `taste` — участвуют в поисковом запросе и в промпте реранка; этого достаточно для сценарных подсказок («на двоих», «обед в офис», «день рождения»).

**Alternatives considered**: выражать «полегче» тегами вместо калорий — теги приходят из каталога и не гарантируют наличия нужного; отсекать образец на этапе валидации ответа — позже, чем нужно, модель уже потратила место в ответе.

## R8. Исправления в текущем отборе

**Decision**: три дефекта текущего `SuggestionService.getActiveSuggestions` закрываются в рамках этой работы, потому что без них требования спеки недостижимы.

1. **Лимит применяется до сортировки**: цикл обрывается по `filtered.length >= maxSuggestions`, а сортировка по `sort_order` идёт после — в набор попадают первые пришедшие из БД строки в неопределённом порядке (FR-009).
2. **Проверка товаров последовательная**: на каждую подсказку-кандидата — отдельный `findByCity`; на каталоге из 45 подсказок это 45 последовательных запросов (SC-006). Проверки выполняются пакетно/параллельно с ограничением одновременности и кешем на `rn|br|target` с коротким TTL.
3. **`screenContext` сравнивается строго**: подсказка с `screen_context = null` сейчас проходит в любой контекст (условие `s.screenContext && ...`), что противоречит явной раскладке контекстов (FR-018–FR-020). После ввода `screen_contexts` поведение становится явным: пустые контексты = `catalog`.

**Rationale**: это не рефакторинг «по пути», а предпосылки FR-009, FR-018 и SC-006.

**Alternatives considered**: оставить как есть и ограничиться наполнением каталога — тогда 45 подсказок режутся произвольным срезом, а время ответа растёт линейно по каталогу.
