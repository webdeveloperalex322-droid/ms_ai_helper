# Критическая проверка кода

## Аргументы

`$ARGUMENTS` содержит описание функционала и список файлов через пробел.

**Разбор:** токены, содержащие `/`, `\` или расширение файла (`.ts`, `.js`, `.json`, `.sql` и т.д.) — это файлы. Всё остальное в начале строки — описание функционала.

Пример: `/review "импорт продуктов из CSV" src/modules/catalog-import/services/import.service.ts src/modules/catalog-import/dto/import.dto.ts`

## Шаги

1. **Разобрать аргументы** — выделить описание функционала и список файлов.
2. **Прочитать файлы** — использовать `Read` для каждого файла из списка.
3. **Проанализировать** — найти только критические проблемы согласно критериям ниже.
4. **Вызвать `ReportFindings`** — передать все найденные проблемы.

## Критерии (только критическое)

Проверять ТОЛЬКО:

**1. Безопасность**
- SQL/command/prompt injection
- Обход аутентификации и авторизации
- Утечка чувствительных данных (пароли, токены, PII в логах/ответах)
- Отсутствие валидации на системных границах (входящие HTTP-запросы, внешние API)
- SSRF, path traversal

**2. Runtime-краши**
- Необработанные отклонения промисов (`async` без `try/catch`, `.then()` без `.catch()`)
- Разыменование `null`/`undefined` без проверки
- Необработанные исключения, которые уронят процесс
- Несовпадение типов, приводящее к ошибке в рантайме

**3. Целостность данных**
- Несколько операций записи в БД без транзакции
- Гонка данных при конкурентных записях
- Отсутствующий или неверный rollback при частичной ошибке

**4. Необработанные пользовательские сценарии**
- Исходя из описания функционала: какие входные данные или состояния могут сломать эту функцию?
- Пустые/null-значения в обязательных полях
- Конкурентные запросы на один ресурс
- Невалидные переходы состояний
- Пути таймаута и частичного отказа внешних зависимостей

## Что пропускать

- Стиль, именование, форматирование
- Производительность (кроме катастрофической — O(n²) на больших данных)
- Предупреждения линтера
- Покрытие тестами
- Средние и низкие баги

## Правила вывода

- Результаты — через инструмент `ReportFindings`.
- Каждый баг **обязательно** содержит `failure_scenario` — конкретный сценарий воспроизведения: точные входные данные / состояние системы → неверный вывод или краш.
- `summary` и `failure_scenario` — на русском.
- `verdict`: `CONFIRMED` если проблема очевидна из кода, `PLAUSIBLE` если требует дополнительного контекста.
- Если критических проблем нет — вызвать `ReportFindings` с пустым массивом и написать: «Критических проблем не обнаружено».
- Не объяснять что было сделано — только выдать результат.
